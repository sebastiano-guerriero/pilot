# The property dialog

Selecting an element opens the property dialog next to it ([PropertyDialog](../packages/overlay/src/ui/components/PropertyDialog/PropertyDialog.tsx)): a search field, the editors that match, and a footer with the keys.

## Where it sits

Strict rules (`dialogSpot()`, `dialogPosition()`):

1. It picks its spot once, when the element is selected: beside it, on its right, else its left, else overlapping its right edge when the element is too wide for either; level with its top.
2. **Editing never moves it.** The element growing, shrinking or moving (a padding, a width, a display change) leaves the dialog where it is, even if the element ends up under it. Don't re-anchor it to the element's live box.
3. Scrolling moves it with the page: the spot is in page coordinates, and while it's at its spot it's drawn in the page, so it scrolls with no lag (`dialogAnchor`; [page.md](page.md), *Following the page as it scrolls*).
4. It only shifts to stay on screen: when scrolling would take it off, or when it grows taller than the room below. A shift from growing sticks (`raisedSpot`): the spot moves up with it, so when it shrinks again (the `/` menu, a shorter list) its top stays put instead of dropping back. A shift from scrolling doesn't stick.
5. It picks a new spot when another element is selected, or when the window is resized (measuring the element right then).
6. **You can drag it** by a strip along its top edge, over the search's empty top padding (it adds no height), with a grip as the clue. The dragged spot lasts for this selection, still moves with scrolling and stays on screen; selecting another element (or resizing the window) puts it beside that element again. Focus stays in the search, and the drag never reaches the page.

The dialog is never taller than the window: the properties scroll inside it, the search and the footer stay. Rows fade out as they scroll under the search's line and the footer's line. The fades are separate overlays, not a mask on the list, so whatever opens out of the list (a select's menu) isn't cut off. There's no native scrollbar (it takes room on Windows and Linux and looks different in every browser): [ScrollThumb](../packages/overlay/src/ui/components/ScrollThumb/ScrollThumb.tsx) draws a thin thumb over the list's edge, shown while the pointer is over the list or just after a scroll, and draggable.

## With nothing typed

The dialog **lists the editors for every property the element has a value for** (from any source), in the order kept in [editors/listOrder.ts](../packages/overlay/src/editors/listOrder.ts) (`LIST_ORDER`), by group: Layout, Position, Appearance, Effects, Transform, Typography, Interactivity, SVG, Visibility. The project owner keeps that order; every editor that writes properties needs a place there, and `listOrder.test.ts` fails without it.

- The list (and only this one: searching shows the matches alone) is **grouped**: each group starts with its label, and a dotted line separates groups (`groupOf()`).
- Rows a revealing editor shows are set in `LIST_ORDER` too, per value (`rowsOf()`): display's grid and flex rows, position's inset. An editor another one shows as a row (gap under `display: grid`) is left to that one. A row that shows on its own (gap on an element that isn't a grid) is listed right after display.
- The list is taken when the search is empty and kept while you edit, so clearing a value doesn't make its row vanish.
- **With state pills, the list is what's set for them**, read as the fields are (exactly those states: Pilot's changes for them, else the page's rules for them): hover on a button with `hover:bg-…` lists its background. Nothing set for them, the list is empty, and the search adds a property. Before, it listed the element's own properties, each field empty for the state, and nothing said why (the owner's report, 2026-11-25). It's taken again when the pills change.
- **A reset's values don't list.** A property whose value comes only from a rule for every element (`*`, `:where(*)`: `* { box-sizing: border-box }`, Tailwind's preflight with its `margin: 0`, `padding: 0`), or from a rule naming only a kind of element (`button`, `h1`, `:where(input)`) when the value sets nothing of its own: `inherit` (or another CSS-wide keyword) or the property's default (`border-radius: 0`, `background-color: transparent`, `opacity: 1`; the defaults Pilot knows, `css/properties.ts`), isn't listed, or every element would list them (`isFromReset()` in [dom/declared.ts](../packages/overlay/src/dom/declared.ts)). So the preflight's `button, input, select… { font: inherit; color: inherit; border-radius: 0… }` doesn't list on every button, while a project's own `h1 { font-size: 2rem }` and the preflight's `img { display: block }` do (they change how the element looks). The owner's call, 2026-11-27: first every element-only rule counted, which hid the project's own headings; rejected too, only their `inherit`s, which left the preflight's `border-radius: 0`, `background-color: transparent` and `opacity: 1` on every button. The element's own rules (`.card { box-sizing: border-box }`, a `box-border` class) and Pilot's edits still list; searching finds the property either way, with its value. Deciding by value instead (hide `border-box`) was rejected: it would also hide those deliberate settings and Pilot's edits, and leave the reset's margin and padding.
- **A shorthand's implicit reset isn't a value.** `text-decoration: none` sets the line to none and puts the color, style and thickness back to their initial values without naming them; CSSOM reads those as `initial`. Pilot counts them as nothing declared (`isImplicitReset()` in [dom/declared.ts](../packages/overlay/src/dom/declared.ts): the value is `initial` and the rule's text doesn't name the property), so the fields show the initial value dimmed and the list leaves them out. The rule still wins the cascade: a less specific rule's value doesn't show through. `initial` written by the page is a value like any other.
- Size, which writes nothing of its own, isn't listed.
- **While a row changes a value, the others don't render** (`EditorRow` in [PropertyDialog.tsx](../packages/overlay/src/ui/components/PropertyDialog/PropertyDialog.tsx)): during a drag, a scrub or held arrows (a change within the last 400ms, `LIVE_MS`), a row skips its render unless Pilot's changes it could show changed (its signature: the changes on its elements for its properties, their shorthands and longhands, `signatureOf()`, from one read of the history per render), or it moved, or its element, widths, states, search or focus changed. Reading a row's fields (the page's cascade, the computed style) was most of each frame of a drag: with every editor listed, ~12ms of ~17 for 84 rows; now a drag costs about the same with 84 rows as with 6 (~6ms). At any other time every row renders, so nothing it shows from the page goes stale; a row's computed values (the base of steps and drags) are read fresh again at the next render after the drag.
- `LIST_ALL_EDITORS = true` in `PropertyDialog.tsx` lists every editor, set or not (handy while many editors are built together, or to review their design side by side). Keep it `false` in a release. An editor another shows as a row is left out only while it shows it, for the element's value now (`listedEditors()`): with no display set, gap and the grid and flex rows are listed on their own, right after display, as the list of set properties does; the list follows display's and position's values. Before, every revealed editor was left out, so gap was nowhere without a grid or flex.

## Searching

Type a property (`opacity`, `padding`, `radius`…) and the matching editors replace the list; clearing the search brings it back. When nothing matches, the dialog says so under the search ("No property matches “layo”"), rather than showing nothing; not for the `/` modifiers, which have their own menu. The search only finds properties: values are always set in the editor. (Typed values like `pt-4` + Enter are left out on purpose for now; see [roadmap.md](roadmap.md), *Open questions*.)

**The search carries over** from one selection to the next: set col-span on one card, click the next, and the col-span editor is already there. The carried-over query is selected, so Tab/Enter goes into its editor and typing replaces it. It starts empty again once nothing is selected (Esc, the tool turned off, the dialog closed).

### What the search looks at

Only these: the editor's **label**, the **CSS property names** it writes (and their logical equivalents, `padding-inline`), and **Tailwind's class names** (its `aliases`, plus a row label that's neither, like `grid-columns`). There are no extra search keywords ("spacing", "layout"…): they matched things the designer didn't mean (`spa` found padding through "spacing"). Aliases borrow Tailwind's utility names, so a designer who knows them gets there in a keystroke or two.

**An alias is a class Tailwind really has** (`underline`, `grid`, `items-center`), not a bare prefix of a family of classes (`text`, `bg`). An exact alias beats every prefix, so `text` as font-size's alias hid text-align and the other text-* rows, and `bg` as bg-color's hid bg-blend-mode. Those families are found by their prefix instead (`text-lg` is font-size). The one-letter spacing aliases (`p`, `m`, `w`, `h`) are Tailwind's own classes for one editor on purpose.

### Ranking

`searchEditors()` and `matchEditors()` in [editors/registry.ts](../packages/overlay/src/editors/registry.ts), best first:

1. an exact **alias**;
2. an exact label or property name;
3. a prefix (`pad`);
4. a Tailwind class that starts with the query, within its first word or by whole words (`items` → `items-center`, align-items; `self` → align-self; `hue-rotate` → `hue-rotate-90`, filter): it beats a name that only has the word later (justify-items). Not into a later word, so `cols` isn't `col-start`;
5. a later word starting with the query (`spa` → the "span" in col-span, `ite` → align-items, `cols` → `grid-cols`): a word being typed counts;
6. a substring;
7. an **abbreviation**, only when nothing better matches: the query's letters in order in a property name, starting at a word start (`wdt` → width, `mxw` → max-width, `pdg` → the padding rows). Requiring a word start keeps it sensible (`dt` won't match width through its middle letters). Starting at a later word (the "width" in `min-width`) counts as one more skipped letter, so `wdt` prefers width itself. Among several, the fewest skipped letters win, then the shortest name.

Hyphens and spaces are ignored on both sides: `minw`, `min w`, `min-w` and `minwidth` are the same query, and `paddingtop` finds padding-top. Swapped letters (`widht`) aren't handled yet.

The dialog shows:

- **every editor tied for the best match**, if that match is a Tailwind class's first word or better (`w` → width, min-width and max-width; `min` → min-width and min-height; `font` → all five font editors; `content` → display's `contents` and align-content), or an abbreviation skipping as many letters (`pdg` → the four padding rows). A substring-only best match shows just the top editor, so a single letter doesn't flood the dialog. Tied editors keep the registry's order;
- **plus the family** of each editor shown. Editors can declare a `family`: min-width and max-width belong to `width`. A query that lands on the family's main editor brings the whole family, main one first (`w`, `width` → width, min-width, max-width). A query that lands on a member shows only that member (`min-w`, `max-width`);
- no limit for those prefix-or-better ties: they're the family the designer is typing, and cutting one hid it (`font` lost font-variant-numeric). An abbreviation shows at most 4 editors.

Padding shows how far this goes without extra logic: its four sides each carry the Tailwind aliases that include them, so `p` shows all four, `px` right and left, `pt` one. Equal matches show together.

## Variables

A field can take the page's tokens (its CSS variables, [dom/tokens.ts](../packages/overlay/src/dom/tokens.ts)) where a value goes, the ones that fit it: lengths in a padding or a radius (fluid ones too: a `clamp()`, `min()` or `max()` with a length in it; before, only a plain length or a `calc()` counted, and a project's fluid spacing scale was never offered), colors in a color, fonts in font-family, numbers in opacity, shadows in box-shadow's custom field (a value that reads as one: 2–4 lengths, a color, `inset`, each layer; Tailwind's `--shadow-md`) ([TokenMenu/tokens.ts](../packages/overlay/src/ui/components/TokenMenu/tokens.ts)). Two ways to the same list ([TokenMenu](../packages/overlay/src/ui/components/TokenMenu/TokenMenu.tsx)), under the field:

- **Typing `--`** at the start of a field or after a space, `(` or `,`: the list at the caret, filtered as you type, by name or by value (`inter` finds `--font-sans`). The way for anyone who knows the names, and inside a value: `calc(--sp` → `calc(var(--space-4)`, and the typing goes on.
- **The variable button** on the field's right edge (Nucleo's nut-2, filled, drawn at 8px in a 16px target, while the field is hovered or edited; the text then ends 4px before it, with an ellipsis when it's cut, except while being edited, when it scrolls): the same list, to browse without knowing a name. Picked, the token goes where the caret is, in place of the selection: the whole value when the field wasn't being edited.

**In order:** the ones meant for the property first, by their names (`tokenHint()`: the spacing scale for a padding, the radii for a radius, `bg`/`surface` for a background), then the rest in the page's order; what's typed still leads (the names starting with it).

**Opening on what the field holds:** a field holding one variable (`--space-4`) opens its list as a select on its value: that row checked, highlighted and scrolled to (`currentToken()` in [tokens.ts](../packages/overlay/src/ui/components/TokenMenu/tokens.ts)); ↑/↓ move from it, Enter or Esc keep it. In math, the variable the caret is in is the current one, and a pick replaces just it. On anything else (a number, math, empty) nothing is highlighted, and there's no checkmark column: ↓ starts at the top, ↑ at the bottom, Enter does what it does in the field. Typing a bare `--` highlights nothing; a name typed, its first match. Not considered the current one: a variable whose value equals the field's number (`16px` and `--space-4`): two can share a value (`--space-1`, `--radius-sm`), so it could point at the wrong one.

**Tokens in files too:** a project's tokens that never reach the page as CSS variables (a `tokens.json` in the W3C or Style Dictionary format, aliases followed; Sass `$variables`), read by Pilot's process in the project ([tokenFiles.ts](../packages/cli/src/tokenFiles.ts), `POST /tokens`, kept current like the components) while it runs for the site (`npx usepilot`). Listed after the page's, by their own names. Pilot defines each as a CSS variable of its own in a sheet of its own (`--color-brand-primary` for `color.brand.primary`, `setFileTokens()` in [dom/tokens.ts](../packages/overlay/src/dom/tokens.ts)), so a pick previews and is checked like any change; the agent's prompt says what each such variable stands for (`fileTokens` on the change set) and to write the token the project's way, never the `var(--…)`. Tailwind v3 configs are JavaScript, which would have to run: not read yet.

Picked, `var(--name)` goes in (just the name inside a `var(` already); ↑/↓ and Enter or Tab pick, Esc closes the list only. A pick that makes the value (from the variable button, or a variable alone) is applied at once, so the page shows it while the field keeps the focus; one inside math being typed (`calc(--`) waits for Enter or leaving the field, since the value goes on. Before, every pick waited, and the page didn't change until the designer clicked away. The change records `var(--name)` as written (names keep their case), the preview resolves it on the page, and the agent writes the project's form of the token. Rejected: a button that replaces the whole value, alone, since tokens sit inside values too (`calc()`, `padding: var(--a) var(--b)`). The list and the button are approved by the owner. Not yet: Tailwind v3 configs.

**Stepping a token:** ↑/↓ (and the wheel) on a field holding one token move it along its scale: `var(--space-3)` → `var(--space-4)`, `--radius-sm` → `--radius-md`, `--gray-100` → `--gray-200` in a color ([`stepToken()`](../packages/overlay/src/ui/components/TokenMenu/tokens.ts)). The scale is the tokens of the same kind named like it but for the last part, in order of their values when they can all be compared (lengths, numbers), else of that last part (numbers, t-shirt sizes). One token per step, Shift too, and it stays at either end: stepping never trades the token for a number on its own. A token with no scale (`--gutter`), or math (`calc(var(--space-2) + 4px)`), steps from the computed value instead, and the number replaces it (`stepValue()` in [css/values.ts](../packages/overlay/src/css/values.ts)), as the owner asked: the wheel and the arrows always do something. Rejected for math: stepping the number inside it (`+ 4px` → `+ 5px`), less predictable than the value you see. What the field shows counts, even before Enter: a variable just picked (or a value typed) is applied first when a step or a drag starts, and what it steps from is read from the page then, not at the last render. Otherwise a drag after a pick started from the variable applied before it.

**Dragging with Shift along a token's scale:** the drag handle with Shift held on a field holding one token goes along its scale, a token every 8px of drag (`TOKEN_PX` in [useScrub.ts](../packages/overlay/src/editors/length/useScrub.ts), slower than a number's steps so each can be landed on; `tokenAlong()` in [tokens.ts](../packages/overlay/src/ui/components/TokenMenu/tokens.ts)), held at either end; back at the start, the token it held (one undo step, as any drag). With no token that way (at the scale's end already), or no scale, or no token, it drags the number as without Shift (×10) (the owner's call). Only the scale's tokens the page defines count: Tailwind emits the ones it uses, so `--container-md` goes to `--container-xl` when there's no `-lg`. The handle tells the field whether Shift is held (`onScrub`'s `shift`), and the fields with a drag handle pass it on (lengths, split editors' parts, a shadow's lengths).

**A lone token shows by its name:** `--radius-lg`, not `var(--radius-lg)`: the wrapper took the room, and cut the end, the part that tells `--space-3` from `--space-4` (`bareToken()` in [css/values.ts](../packages/overlay/src/css/values.ts)). Inside a value it keeps its `var()` (`var(--space-2) * 3`), and so does one with a fallback. A name typed (`--space-4`, `--a * 2`) goes in its `var()` (`withVars()`), so what a field shows can be typed back. The change still records `var(--name)`. Considered for names still too long: cutting them in the middle (`--color-b…primary`), which only reads well for one name; for a value of several parts (`10px 20px`, `repeat(3, 1fr)`) it hides the structure. Not built for now.

**Hovering a field says what it can't show** (a tooltip, at the field's right edge; not while it's being edited, when what's typed hasn't been applied):
- **Cut** (an ellipsis): the whole value. Measured as the pointer comes, since the variable button then takes room.
- **Math** (`100% - 20px`, `var(--space-2) * 3`, `clamp(…)`): what it comes to, `= 180px` (`mathResult()`), from the moment it's applied, with the pointer still on it; both when it's cut too (`100% - 20px = 180px`).
- **A lone variable** (`--color-white`, `--text-sm`), cut or not: its whole name, then its value, dimmed (the owner's call, 2026-11-25: the field never shows the value, so the tooltip always does; before, `= 14px` only). The value as the page's root defines it, other variables in it resolved, so it reads as the code does (`#dbe6fe`, Tailwind's `oklch(…)`), else what the field's property computes to (a variable set on an element, not the root); a length's px too when it's defined otherwise (`0.875rem = 14px`); cut at 40 characters (a font stack). Read when the pointer comes (`soleVariable()`, `variableValue()` in [PropertyInputText](../packages/overlay/src/ui/components/PropertyInputText/PropertyInputText.tsx); the Tooltip's `aside`, drawn as a shortcut is). One with a fallback (`var(--a, 4px)`) isn't one value: it's shown whole, as any cut value.

Fields show declared values, never computed ones; the tooltip is the one place a computed value shows, beside the declared one, never in its place. Every field sits in a tooltip, empty when there's nothing to say, so the input is never made anew (and loses focus) when there comes to be.

## Modifiers: widths and states

Typed at the start of the search, shown as **pills** in a row above the field. More modifiers will sit there side by side later.

### The `/` menu

For discoverability (nobody guesses `from-1200`): typing `/` at the start of the search lists the **modifiers** inside the dialog ([search/modifiers.ts](../packages/overlay/src/search/modifiers.ts)), each with a name, its syntax and a short description: **From width** `from-768`, **To width** `to-767`, **No breakpoint** `base`, **All widths** `all-widths`, **Hover** `hover:`, **Focus** `focus:`, **Focus visible** `focus-visible:`, **Active** `active:`. Words that match none offer **Create modifier**, a condition in words (*Conditions* below).

- **Used on the element come first**, marked (the name in the accent, a line before the general ones): every states and width combination something sets a property of it in, the project's rules and Pilot's changes, each with what it sets as its description (in the dialog's own order, LIST_ORDER, so it reads like the list it leads to, unknown properties last; one line, cut with an ellipsis): **Hover** `hover:` *background*, **Hover, from 768px** `hover:from-768`, **from 768px** `from-768` *padding* (`usedModifiers()` in [search/used.ts](../packages/overlay/src/search/used.ts)). States first, then widths from the narrowest, then both. Picking one sets exactly its pills, its states and its width chip or none, so a combination (`dark`-style complex ones included, as they come) is found without guessing, and the list then shows what it sets. Read like the pills: the element's own states (not `.card:hover .title`), width conditions and capabilities true now, no rules for every element (a reset's `*:focus`). A state used alone takes its general row's place. A long name or syntax (`Dark + Focus visible + Active, from 1200px`) shares the line with the other, both cut with an ellipsis; so does a long modifiers' pill, on its one row beside `default`. The owner's call, 2026-11-26; the look is a first pass.
- Typing after `/` filters by any word of the name or syntax (`/fr`, `/width`). ↑/↓ move, Enter or Tab picks. The menu scrolls past seven rows and a half (the cut row says there's more), with Pilot's scroll thumb, the highlighted row kept in view, and rows fading under its top and bottom edges where there's more to scroll to (none at either end; the owner's call, 2026-11-26). The width list after `from-` is the same menu.
- Picking a state, Base or All widths sets its pill at once. Picking a width puts its syntax in the search to finish typing (`from-`, with the window's width suggested).
- Esc closes the menu and clears the `/…` text, since it isn't a property search (the dialog stays open).
- No property starts with `/`, so it never gets in the way, and what follows `/` never searches properties (it did: "if it has", on its way to Create modifier, showed aspect-ratio for its "as"). The placeholder says so: "Add a property, or / for modifiers".
- More modifiers (`*`, group-checked…) are one entry each in `MODIFIERS`; what they do once set is their own work. The rows' look is a placeholder, pending design.

### Viewport widths

Without the **width chip** ([edits/widths.ts](../packages/overlay/src/edits/widths.ts)), a change goes to **the rule that applies at the window's width** ([edits/reach.ts](../packages/overlay/src/edits/reach.ts)), and the field shows that rule's value: with `pt-2 md:pt-4 lg:pt-12` and the window between md and lg, padding-top shows and changes `md:pt-4`'s; resized past lg, it shows `lg:pt-12`'s, and the next change goes there. A row whose value changes that way, with the window and not an edit, says it updated: its property name turns the accent and fades back to its own color in a second (`flashRow`; resizing within the same rule doesn't). Only the names whose values changed: one of display's rows (grid-columns, not every grid row), one of margin's stacked sides (margin-top); display's own value changing changes its rows, so all of it. Before, the whole editor flashed, and with display's grid rows nearly every name turned green for one value. The name rather than a tint behind the row, which some rows would lose. The project's rules already say where a value applies, so Pilot follows them (the owner's design, 2026-11-26). Each property follows its own rules: a shorthand whose sides go to different rules (`pt` at md, the rest base) is written per side, and each selected element follows its own (several selected with different reaches: how the UI says it is open, [roadmap.md](roadmap.md)). Where nothing declares the property, it's the base. The chip says otherwise on purpose: a value set with it stays there whatever the window. Before (earlier the same day), a change without the chip was always the base value, at any width: at 1200px a change to `p-10 lg:p-14` didn't show.

- **Where the values apply**, while a property is in use (its field focused, dragged or just changed) and it has rules for some widths: the ruler at the top shows ([page.md](page.md)), with a bar under the breakpoints per run of widths where one of its values applies (`spansOf()`): green where the change goes, grey for its other rules, none where nothing sets it. Where each value applies, not how the media query is written: `md:` has no end, but its bar ends where `lg:` takes over (the owner's call). A "from" rule overlapping a "to" one is an edge case, a CSS mistake: whichever wins shows. Rules for conditions other than width (dark mode, print) aren't on the bars yet (open). A device capability true now (`(hover: hover)`, `(pointer: fine)`) is no condition: it holds for the whole session. Tailwind v4 puts every `hover:` in `@media (hover: hover)` (no hover effects on touch screens), so `hover:bg-…` is the hover rule and `md:hover:bg-…` hover from 768px, followed as the window resizes like any other (`mediaRange()` in [dom/breakpoints.ts](../packages/overlay/src/dom/breakpoints.ts); before, the hover pill found nothing there). Pilot's own preview doesn't add the query: beside the project's rule it's inside it already, and the designer's screen has a pointer; the code is the agent's, in the project's conventions. The ruler is the window, so a run past its width is cut at the right edge, square there (clipped, not ended); each bar's tooltip has its widths and value. Meanwhile the ruler shows only the widths where the bars meet (Pilot's own ranges too), and not the window's width: the page's other breakpoints change nothing for this property, and the green bar running to the right edge already says where you are (the owner's call). Of those, the ones between two grey bars are dimmed, only the green bar's ends bounding the edit: the grey bars' background, the text dark on a light page and light on a dark one. Pilot reads the page's color under each (`colorBehind()` in [dom/backdrop.ts](../packages/overlay/src/dom/backdrop.ts): the elements under it, their background colors composited), again as the page scrolls, since CSS can't: Pilot's layer is isolated from the page, so blending can't see it, and a filter can't draw the digits in Pilot's font. Over an image or a gradient there's no one color: white text with a white ring. Hovering the ruler, or resizing, shows all the breakpoints and the width again, at full strength, to pick another. The look is the owner's (2026-11-26): the labels move under the bars, and two bars meet in the middle of the breakpoint between them, its tick's pixel the gap, and the first starts 1px from the left edge (`spanBox()`). To draw the eye, the green bar breathes twice as it comes in, its fill to the full accent and back at the pace of the elements with a job on them, and again for each property that comes into use (none with reduced motion; a wave sweeping across it was too subtle). The grey bars are black at 20% over white at 40% (a light ring, inside or out, made them look blurred on a light page).
- **No breakpoint** (`base `, or the `/` menu; named *Base* at first, which didn't read as a breakpoint choice, the owner's call): the value without a media query, at any width: what was set for smaller screens, without resizing. **All widths** (`all-widths `): the base value, with the property's breakpoint rules removed (the project's, as removals, [edits.md](edits.md), *Removing a value*; Pilot's own dropped), so the one value applies at every width; one undo step. The removals go to the agent like any other.

- **Type** `from-1200` then a space: the modifiers' pill reads `from-1200` (as typed), and the rest is the search (`from-1200 pt` searches `pt`). `to-767 ` is `to-767`, and both make a range: `from-768 to-1199 ` is `from-768:to-1199`. Typing another token replaces that end. A token counts only once followed by a space, so `from-12` on the way to `from-1200` isn't taken.
- **Click** the viewport width ([page.md](page.md)): the chip becomes `from` that width; **Shift+click** makes it `to`. ### States

- **The color scheme**: `dark:`, and `light:`, styles for light mode only (Tailwind has no `light:` of its own; projects add it, and Pilot offers it). Pilot's own rule for a scheme the project has no rule for is written the project's way too: its class or attribute when its rules use one (light, with only a dark class: what isn't dark, `:not(.dark, .dark *)`), else the media query. One scheme at a time: `light:` replaces `dark:`.
- **Pseudo-elements**: `before:`, `after:`, `placeholder:`: the change is for the element's `::before` (`::after`, `::placeholder`), not the element. ## Keys

| Key | Where | Does |
| --- | --- | --- |
| type | search | Finds the property. Tailwind aliases work: `p`, `pt`, `px`… |
| **Tab** or **Enter** | search | Jumps into the matched editor. What you typed decides the focus: `pt` → top, `pl` → left |
| type a number | editor | `12` or `12px`. ↑/↓ change it by 1, by 10 with Shift; a token, along its scale (*Variables*) |
| wheel | editor, being edited | Like ↑/↓: up is ↑, one step per notch (or per 24px of a trackpad's scroll). A burst of steps is one undo step. A field not being edited lets the dialog scroll |
| **Enter** | editor | Applies the value and returns to the search, text selected, ready for the next property |
| **Tab / Shift+Tab** | editor | Next/previous field (padding: top → right → bottom → left), on into the next/previous editor. Past the first or last, back to the search |
| **Esc** | anywhere in the dialog | One level back: editor → search (discards typed text) → clears the search → closes the dialog |
| **Esc** | page, nothing selected | Turns the select tool off |
| double-click | a text on the page (Select) | Edits it in place: **Enter** done, **Esc** cancels |
| **Cmd/Ctrl+Z**, **Cmd/Ctrl+Shift+Z** | anywhere | Undo / redo |
| `from-1200` / `to-767` + **Space** | start of the search | Sets the width chip |
| `hover:` `focus:` `focus-visible:` `active:` | start of the search | Sets a state pill |
| `/` | start of the search | Lists the modifiers |
| **Tab** after `from-` / `to-` | search | Takes the suggested width |
| **Backspace** | start of the search | Removes the last pill |
| click / **Shift+click** | viewport width | Width chip `from` / `to` that width; a second width makes a range |

```
pt ⇥ 24 ⏎    px ⏎ 6 ⏎    …
```

Linked values follow Tailwind's meaning: `px` links left and right, `py` top and bottom, and `p` all four, so one number sets them all, as one undo step.

**The footer** always shows the keys for what you're doing: in the search, "**Tab** or **Enter** to edit"; in a property, "**Enter** to apply, **Esc** to go back" (editors can replace it for a moment, `onHint`). The keys are `<kbd>` elements and the footer carries `data-area="search" | "editor"`. The copy never names a property: every editor follows the same keys, so the messages stay the same for all of them.
