# Agent handoff

The handoff is **jobs**. Edits, tasks (Make responsive) and comments each go to the agent as a job; the agent applies it; Pilot checks the result on the page. The page is the source of truth for its jobs.

```
page (your app in dev, the overlay)          one hub per machine and version, 127.0.0.1:4756
  Send ──POST /jobs──────────────────────▶  ┌───────────────────────────────────┐
  job updates, launch ◀──SSE /events───────  │ jobs and runners, by page origin  │
  follow-up ──POST /jobs/:id/retry───────▶  └───────────────────────────────────┘
                                               ▲ in-process            ▲ HTTP
                                 project A's dev server        project B's `npx usepilot`
                                 (Pilot in it: runs the hub)   (joins it, takes over if A stops)
                                       │ one run per job, the prompt on stdin
                                       ▼
                                 claude -p · codex exec · cursor-agent -p
```

## Agent runs

**Pilot runs the agent itself, once per job** ([run.ts](../packages/cli/src/run.ts), [agents.ts](../packages/cli/src/agents.ts)). `npx usepilot`, in the project's folder beside the dev server, joins (or hosts) the hub, registers for the site, and for each job starts the agent's command-line tool in the project's folder: the prompt on stdin, its JSON output read for the reply and the session. Nothing waits in an agent's chat.

**Why** (2026-11-20). The first design parked an agent's chat inside an MCP tool call (`pilot_wait_for_edits`), and it couldn't be made reliable: Cursor caps a turn at 25 tool calls and pauses it (every few Sends the designer had to find the chat and press Resume), MCP clients time idle calls out, a chat had to stay open and listening, and a comment thread's follow-up went to whichever chat was free, without the context of the first. Running the agent per job has none of that: every Send works, whenever. Tested on macOS with Claude Code, Codex and Cursor, on a test page and on nucleo-2 (8,000 files): edit jobs in 10–25s, comments in 15–35s, two jobs at once in the same file both landed.

- **Agents:** Claude Code (`claude -p`), Codex (`codex exec`), Cursor (`cursor-agent -p`). Each is an entry in `AGENTS`: its executables, how to install it and sign in, its sign-in check, its flags, and how to read its output. Gemini (`gemini -p`), Copilot (`copilot -p`) and opencode (`opencode run`) have the same three things (one task and exit, a session id, resume by id), by their own help: not added yet.
- **The agent:** `--agent`, else the one saved for the project folder (in `~/.config/usepilot/projects.json`, never in the repo: a teammate may use another). `init` saves the agent whose chat runs it (`agentFromEnv()`: the setup prompt runs inside the agent, which its environment tells), so `npx usepilot` normally doesn't ask. With none saved, the only one signed in; with several, it asks once in the terminal (the owner's call: detection first, a simple question as the fallback). Each sign-in check takes about a second.
- **The site: the page says its project.** Each page's loader names its project (`mountPilot({ project })`, its package.json's `name`, written by `init`: `loaderCall()` in [init.ts](../packages/cli/src/init.ts)); the page sends it with `/events?project=`, and `npx usepilot` takes only a page with its own project's name (`projectName()` in [config.ts](../packages/cli/src/config.ts)), whatever its address, so a teammate on another port works too. It never takes another project's page: each one it sees and leaves is said once in the terminal, with why ("open on … for *playground*, not *nucleo*"; "its loader doesn't say which project it is: … update"), and the page's toolbar names its project ("Pilot isn't running for *shop*"), or says its loader names none. `--url` skips the check. **Why** (2026-11-21): taking the first local page with Pilot open picked the Pilot playground open in another tab instead of nucleo-2. Rejected: asking in the terminal (the owner didn't want it), the agent writing the dev address down at setup (breaks when the address changes, or a teammate opens it another way), and recognizing the page from its files and texts (a heuristic).
- **Permissions: the agent's own, as in its chat** (checked by [scripts/agent-runs-check.mjs](../scripts/agent-runs-check.mjs) on macOS, and on Windows and Linux by the **Agent runs** workflow). A run can do what the designer allowed that agent (its settings, allow rules, MCP servers, skills), and edit the project's files, which is the job; what its chat would ask about is refused, since no one is there to answer, and the agent says so in its reply. **Pilot says it too, briefly, after the agent's reply** (in the thread and the terminal; `refusedNote()` in [agents.ts](../packages/cli/src/agents.ts)): what was refused ("the `nucleo-icons` MCP server", "running `cat`, `cd` and `curl`", "reading files outside the project"). **Only an MCP server or a website can be allowed from there**: the reply gets a **Copy instructions** button (`Job.allow`, the thread's `CopyAllow`) that copies a request for the agent's chat ("Allow the nucleo-icons MCP server in this project's Claude Code settings (.claude/settings.local.json), so Pilot's runs here can use it."), never shown in the reply; the agent edits its settings and asks the designer to confirm, as it does (it knows its settings' format; each agent's `projectSettings` names only the file). Narrow, and the designer's own: one server they installed, one site, in the project's settings, not every project's; an MCP server's request allows all its tools, and the note names it, so the designer decides. **Never a command** (the owner's call, 2026-11-24: security first): a run's commands can do anything (`curl` sends files anywhere or fetches a script, `node` and `python3` run any code), and allowing one allows every future run, whatever a skill, the page's text or an attachment tells it; so the note only names them, by program, each once. Most need no allowing: the prompt has every agent read and search with its own file tools, not `cat` or `grep`, and leave the page to Pilot, not `curl`, which were most of what runs were refused (a skill's checks). Files outside the project: named, nothing to allow. Pilot never allows anything itself: a button that did would be clicked by the page's own scripts too. Before, the note gave each settings rule, then a request in a code block that allowed commands too. The same for every agent: what was refused is one of four kinds (an MCP server, a command, a website, another tool: `Refused`), which every agent lists in its reply's `pilot` block (the prompt asks); Claude Code's own list in its output (`permission_denials`) is added. Cursor's and Codex's rules come from their docs (2026-11-24), not yet seen in a refused run. **Only said, never done for the designer** (the owner's call: security first): no Allow button, since the page's own scripts can click Pilot's buttons, and text on the page goes into the prompt, so a page could get an agent refused something and then allowed it. Asking during the run (Claude Code's `--permission-prompt-tool`) was rejected too: Claude Code only, and the run would wait on the designer. **Why** (2026-11-24): the Nucleo skill's tools, approved in the designer's chat when it asks, were refused in every run, and the reply only said they "weren't allowed to run here". Never a flag that skips permissions. Claude Code runs with the designer's settings in `acceptEdits` (`-p` refuses what would prompt: checked, so not `--permission-prompts none`, which older versions don't know). Codex runs in its sandbox in the mode its chat uses for a project (`-s workspace-write`: writes in the project and the OS temp folder, which `git` needs), the rest from the designer's config (network, web search, rules); `exec` never asks. Cursor runs in its allowlist mode (`--sandbox disabled`, never `--force`): what the designer's allowlist doesn't allow is refused. Not its sandbox: it doesn't exist on Windows ("requires macOS or Linux"), and on Linux it fails on Ubuntu's default AppArmor settings (it needs unprivileged user namespaces); found by the Agent runs workflow, where both modes passed every check once the sandbox could start. **On Windows**, Codex's sandbox needs a mode or every run is read-only (every command "blocked by policy"): `windows.sandbox="unelevated"`, which needs no admin rights; both modes passed on GitHub's Windows machines.
  - **Why** (2026-11-21). Pilot is a different way to ask the designer's agent, not an agent of its own, so a run does what the chat does: no more, no less. Until then each run had Pilot's own limits (the project's files only, no shell, no internet: Claude Code `--restricted` with five file tools, Codex's web search off), stricter than the chat: "make my footer like Linear's" couldn't look at Linear's site, and skills that need a tool couldn't work. Rejected: skipping permissions (`--dangerously-skip-permissions`, `--force`) so nothing is refused: no one watches a run, and part of a prompt isn't the designer's (the page's text, attachments, a skill someone else wrote), so an instruction hidden there would run unchecked. Asking the agent's permission requests in the thread, with Allow and Deny, was planned next, then set aside (2026-11-24): Pilot says what was refused and how to allow it, and the designer changes their settings (above).
- **The prompt goes on stdin**, never as an argument: no quoting or length limits on Windows (npm's `.cmd` shims need a shell; their arguments are only Pilot's flags, session ids and paths). It's the job's prompt in its run form (`run: true` in `formatPrompt()`, through `jobPrompt()`): the guidelines in full (a fresh run hasn't read them; one line for a session of the editor's that has, below), the agent doesn't check its edit afterwards (Pilot checks the page: Codex otherwise ran `git diff` and a script after each edit, 2–3 calls), a refused command stays refused, so it isn't retried another way but listed as `refused` (a Cursor run tried `git show` five ways, a model round each), the reply is the notes, a question or a props list goes in a fenced `pilot` block at its end (JSON, read by `replyOf()`), and tasks work out widths from the code: Pilot measures them after the run and sends problems back once (the follow-up it always had). The text files attached come in the prompt; images by path (Claude Code may read the attachments' folder, `--add-dir`; Codex gets them with `-i`).
- **The editor's sessions** ([pool.ts](../packages/cli/src/pool.ts)): a Send's job resumes a session kept for the editor's jobs, instead of starting one. The agent has read the guidelines and the code it touched, so the prompt says them in one line ("the same as for the earlier edits in this session") and the job takes fewer steps. A free session is taken; jobs at once each take their own (a session never runs twice at once), so there are as many as jobs ever ran together, at most the runner's slots. They're saved with Pilot's settings for the project folder (`projects.json`, per agent), so `npx usepilot` finds them again. A session is retired after 20 jobs or a day, before its context slows the agent down, and dropped when resuming it fails (the job then runs in a new session, the guidelines in full). A job's follow-up resumes its own session, waiting for it if another job has it. Comment threads keep their own sessions, below. Rejected: one session for every job (two jobs at once would run in it together), and a new one per Send (every job reads the guidelines and the code again).
- **Sessions:** a job done carries its agent session (`Job.session`, `{ agent, id }`). Its follow-up and the answer to its question resume it; a comment thread keeps the last one (`CommentThread.session`) and its next message resumes it, so the agent remembers the thread. Only the same agent's session is resumed, and only a plain id (letters, digits, dashes: `sessionOf()`, since it becomes an argument). A session that's gone costs nothing: every comment carries its whole thread, and a run that fails without a reply runs once more without the session.
- **An agent's tool older than Pilot's flags** fails every run. Found on the bench lab (2026-11-24): a year-old `cursor-agent` didn't know `--trust` or `--sandbox`, exited at once, and the job said only "The agent printed nothing". So `npx usepilot` reads the tool's help when it starts (`help` in `AGENTS`, `missingFlags()` in [agents.ts](../packages/cli/src/agents.ts)), compares it with the long flags Pilot runs it with, and says in the terminal when some are missing; a run that fails checks again (it may have been updated since) and says it on the page too. **In plain words first**, since a designer may be reading: "Cursor needs an update · This version of Cursor can't work with Pilot yet. In a terminal, run cursor-agent update, then send again." (`errorFor()`, `outdatedNote()` in [run.ts](../packages/cli/src/run.ts)); the flags only in the terminal, last, for whoever wants to know why. Only said, never a reason not to run: a help worded unlike Pilot expects mustn't stop a tool that works, and one it can't read says nothing. Not for a stand-in `bin`.
- **Errors:** a run that fails reports the job done with an `error` (title, what to do): "Claude Code isn't signed in · Run claude auth login in a terminal, then send again", or "couldn't do this job" with the line that says what went wrong (the agent's own error rather than Pilot's generic "printed nothing", which gets the exit code when there's nothing else), and the terminal prints the last lines of what it said. A failed run is tried once more first (Cursor once returned nothing in half a second), except a sign-in problem. The page says it at once where stuck jobs are (*When something's stuck*), and the job's changes are unsent again, still previewed, for the next Send.
- **At once:** up to five jobs run together (`SLOTS`); five, not three (2026-11-24): a burst of six comments in 23s on the bench lab left the two sent while three ran waiting about 10s each for a slot, and three at once made no job slower ([benchmark.md](benchmark.md), B1); the page never sends two on one element at once (*Elements being worked on*). Stop (the loader's X) cancels the job, and the runner, which checks every 2s, kills the run.
- **The terminal** shows one line per job (what it is, then the time and the reply's first line, or what went wrong). Ctrl+C stops Pilot.
- **Speed:** each agent step costs 3–4s (a model round trip), so a job is about as fast as the steps it needs: the code's location Pilot finds (*The loop*) and the edit guidelines' "no screenshots, builds or tests" matter as much here. Measured, and what's next, in the roadmap.

Until agent runs (0.13 and earlier), an agent's chat ran Pilot: `/pilot` called `pilot_launch`, then waited for jobs in `pilot_wait_for_edits` and reported each with `pilot_done`, on Pilot's MCP server. It's gone; `usepilot mcp` remains only to tell an old setup what to do.

## Starting with the dev server

**Pilot starts with the app's dev server**, so nobody runs `npx usepilot` ([dev.ts](../packages/cli/src/dev.ts)). The same runner, in the dev server's process: Vite's plugin (`pilot()` from `usepilot/vite`, [vite.ts](../packages/cli/src/vite.ts), for Vite and the frameworks on it: SvelteKit, Astro, Nuxt, React Router), Next.js's `withPilot(config)` (`usepilot/next`, [next.ts](../packages/cli/src/next.ts)), and for any other dev server its script run through `usepilot dev -- <command>` (in package.json, `"dev": "usepilot dev -- ng serve"`). `init` sets up the one that fits (*Installing*). `npx usepilot` stays, for a dev server none of these reaches (a PHP site), and for `--agent` or `--url`.

- **Development only**, like everything Pilot sets up: Vite applies the plugin only while it serves (`apply: "serve"`, never in a build or `vite preview`), `withPilot` starts it only in Next.js's development phase (`phase-development-server`: never in `next build` or `next start`), and every way refuses a production process (`NODE_ENV=production`) and CI, where a dev server started for tests must not run anyone's agent (`devGuard()`). It only ever runs for local pages, as `npx usepilot` does.
- **Once per dev server.** Next.js reads its config in more than one process: the first one to start Pilot sets `USEPILOT_RUNNER` to its process id, and a child that sees it (alive) doesn't start a second. A dev server that restarts (Vite on a config change) closes its runner and starts a new one. `usepilot dev` starts Pilot before the dev server, so a dev server that also starts it (`withPilot` under `usepilot dev`) sees it running.
- **Never fails the dev server.** What goes wrong is said in its log (`[pilot]` lines, Vite's logger for the plugin), never thrown.
- **The site:** the plugin passes Vite's own address once it listens; the others find the page by the project's name, as `npx usepilot` does.
- **Why** (2026-11-26): `npx usepilot` was a second terminal to remember every day, and forgetting it was the most common stuck state ("Pilot isn't running"). Rejected: a plugin per framework (a dozen; `usepilot dev` covers the rest with one line in package.json), and having init edit config files itself (the agent writes them the project's way, as it writes the loader).

### Before the agent is ready

Pilot started with the dev server **doesn't wait for the agent to start** (`waitForAgent` in [run.ts](../packages/cli/src/run.ts)): with its command-line tool not installed, or not signed in, Pilot still opens on the page. The designer can select, edit and preview right away; what they send waits in the hub's queue, and runs once the agent is ready, with no restart (Pilot looks again every 3s, `readiness()`). `npx usepilot` keeps failing at once with what to do instead: someone is there to read it.

- **The page says what to do**, through the agent's `setup` (`AgentSetup` in [bridge.ts](../packages/protocol/src/bridge.ts)): its state (not installed, not signed in, signing in), the agent's name, the command to run (installing it with the platform's command: PowerShell's on Windows, `installCommand()`). Shown as a stuck state (`setup`, *When something's stuck*): "Sign in to Claude Code · Click Send to open its sign-in page, or run claude auth login in a terminal. What you send waits until then"; not installed, it says to ask the agent to install it first (the designer has its chat open: it set Pilot up), else the command. The agent it waits for: the one saved for the project (`init` saves the setup chat's agent even before it's installed), else the first one installed, else any, once one is.
- **Sending signs in.** While the agent is installed but not signed in, sending something (Send, a comment, a task) asks the runner to start the agent's own sign-in. Send does it with nothing new to send too, and so does a comment that waits for the job on its element: what waits was sent while the agent wasn't installed yet, and Send is where the page says to click (its tooltip says "Opening the sign-in page"). Found 2026-11-26: until then only a new job signed in, so a designer who had sent before installing had nothing to click. The sign-in is the agent's own (`POST /setup/sign-in`, `login` in `AGENTS`: `claude auth login`, `codex login`, `cursor-agent login`): it opens its page in the browser, and what was sent goes once they've signed in. While it's under way the page says so, with the sign-in page's address when the agent printed one (only an https address: `setupOf()`). Nothing is typed into it: a sign-in that asks for a code in the terminal ends at once, and the page says to run it in a terminal (as one that times out after 5 minutes does). The command is the agent's own, fixed: nothing from the page goes into it. **Why** (2026-11-26): signing in in a terminal was the install's first step, before the designer had seen anything. Rejected: a Sign in button (the toolbar's look is the owner's; sending is the moment it's needed), and Pilot signing in through an agent's SDK (Anthropic's Agent SDK terms don't let other products offer claude.ai's sign-in; running the designer's own installed tool, signed in with their own account, is what Pilot does for every job).
- **Each agent's real sign-in, started this way** (the Sign-in workflow, 2026-11-26, on macOS, Windows and Linux): Claude Code, Codex and Cursor all print their sign-in page's address (`claude.ai/oauth/authorize`, `auth.openai.com/oauth/authorize`, `cursor.com/loginDeepControl`) and keep waiting for the browser, with no terminal and nothing typed. Signing in to the end with a real account isn't checked (a sign-in can't be finished on a CI machine); Pilot's side of it is, with stand-ins ([run.test.ts](../packages/cli/src/run.test.ts), `scripts/dev-server-check.mjs`).

## Installing

The user pastes one prompt into their agent: run `npx usepilot@latest init` and follow what it prints ([init.ts](../packages/cli/src/init.ts)). The user never edits code by hand, and never opens a terminal (signing in happens on the page, *Before the agent is ready*):

- **The command does what must be exact:** it installs `usepilot` as a dev dependency with the project's package manager (from the lockfile, up to the repository's root), checks the agents' command-line tools (`detectAgents()`: installed, signed in) and says which Pilot will run (`--agent`, else the setup chat's agent, is saved for the project, ready or not), and removes Pilot's old chat setup wherever it finds it ([legacy.ts](../packages/cli/src/legacy.ts): its MCP server in each agent's config, the `/pilot` skill, from before agent runs; only Pilot's entries and files). Nothing is added to the repo. Run again, it changes nothing.
- **The agent does what needs judgment:** the command detects the framework (Vite, Next.js App and Pages Router, Nuxt, SvelteKit, Astro, React Router, Angular, Gatsby, Rsbuild, Parcel, and webpack with the tools built on it: Create React App, Vue CLI, Rspack) and prints the snippet that loads Pilot in development only, and where; the agent writes it the project's way. Each snippet's check is one the build replaces, so a production build drops Pilot entirely: checked by building a sample of each new one (2026-11-24) and searching the output. **Angular uses `ngDevMode`, not `isDevMode()`**: `isDevMode()` is decided in the browser, and the production build kept Pilot's files (never loaded, but shipped). **Parcel** ignores a package's `exports` unless the project opts in, so `usepilot` has a `main` too: without it, Parcel couldn't load Pilot in development. A site with no bundler Pilot knows (PHP, Rails, Django, plain HTML) gets one tag in the shared layout, printed only when Pilot's own file is on disk (a dev dependency, never deployed: the agent checks the deploy rules, or asks) **and** the project's own development setting says so; never from the request (the Host header and the client's IP can say anything behind a proxy, or from a client). **Pilot never runs in production**, whatever the loader: `mountPilot` does nothing on a page that isn't on a development address (`isLocalHost()` in [bridge.ts](../packages/protocol/src/bridge.ts): this machine, local names like `*.test` or `nucleo`, private networks), not even its shortcut. An app that loads Pilot already gets no such step. It names a file only when it found it, and otherwise says what to look for: a guessed path that doesn't exist sends the agent searching. A Vite app whose pages load no module of their own (classic scripts) may deploy its HTML as it is, without Vite building it, so its HTML isn't touched: Pilot is injected from the Vite config by a plugin that only runs while Vite serves (`apply: "serve"`, `transformIndexHtml` before Vite's own processing, so the package resolves).
- **The agent installs the agent's command-line tool** when it's missing: the setup chat's own agent, with its own installer (the platform's: PowerShell's on Windows), after asking the user. Signing in isn't a step: Pilot asks for it on the page.
- **The agent sets Pilot to start with the dev server** (*Starting with the dev server*): the plugin in the Vite config (Astro's and Nuxt's under `vite.plugins`), `withPilot` around Next.js's config, else the dev script through `usepilot dev` (`devServerStep()`): `dev`, or a `start`, `serve` or `develop` script that runs a dev server (`ng serve`, `gatsby develop`…), never one that may serve production (`next start`, `node server.js`). A script of several commands goes whole, in quotes; one with quotes of its own isn't wrapped. Found already there, it's said done. With none of these, the user runs `npx usepilot`.
- **The agent tells the user** to restart the dev server and open the app (or, without the dev server setup, to run `npx usepilot` beside it).
- A monorepo's root gets the list of its apps instead, to run it in the right one.

### Updating

`npx usepilot@latest update`, in the app's folder ([update.ts](../packages/cli/src/update.ts)). It installs the latest `usepilot` with the project's package manager, removes Pilot's old chat setup (as `init` does), and prints the version change and what's left, for a designer to read as much as for an agent: `init` again when there's something new to set up (Pilot starting with the dev server, the loader naming the project), restart the app's dev server (its bundler keeps the old Pilot until then, and Pilot starts with it) or `npx usepilot`, and, when the bridge version changed (read from the old bundle before it's replaced: every file of its CLI, which is in a few since `usepilot/vite` and `usepilot/next`), update the other projects too.

- **Why a command of its own:** `init` is setup, safe to run any time, and never changes a version you have (as `shadcn init` and `prisma init` don't); upgrading is a deliberate step, as with `storybook upgrade`. `init` on a project with an older Pilot leaves it alone and says that `update` updates it.
- **An old chat setup that's still there** (a project not updated, an agent's config `init` couldn't edit) starts `usepilot mcp`, which now only says, in the agent's MCP log, to run `update` and `npx usepilot`.

## Finding the code, and the time

- **Pilot finds the code first.** The runner runs in the project's folder, so before it hands over a job it searches the project for each element and adds where its code probably is, with the lines around it ([locate.ts](../packages/cli/src/locate.ts)): the agent can go straight to the edit instead of searching. When the page named the element's component, it looks in that component's file first (found by name when the page couldn't name the file: [page.md](page.md), *Components*).
  - **No one detail is enough.** Classes repeat across a project (`flex`), text comes from data, and the same markup is often copied. So the page sends, with each element, what it shows of it (`ElementTarget.context`, `elementContext()` in [target.ts](../packages/overlay/src/dom/target.ts)): its texts, each on its own; the attributes that say what it is (`href`, `alt`, `style`, `data-*`…); its parents' tags and classes; the texts right before and after it; and the heading of its section.
  - **Each tag in the code is weighed on all of them.** Its classes count by how rare each is in the project, and against it when the code writes classes the element doesn't have, or misses some it has (`gap-2` isn't `gap-4`). Template code is read for what it writes as is (`class="container <?php echo $class ?>"`, `className={cn("flex", …)}`). Also counted: its texts and attributes in its contents, the texts beside it just above and below, its nearest heading in the code being the page's, and its parents found by matching the tags between (indentation can't be trusted). The code writing a text other than the element's counts against it, and so does any text where the element has none.
  - **The page's address helps.** A file named like the page's path is likelier. When the path names one of the project's folders (a PHP site served from `web-3`), the project's other sites (folders with their own index file: `web-2`, an older copy) are left out.
  - **One place, two, or none.** A place is said when it has two kinds of evidence (its classes and its text, its parents…), its id, or classes distinctive enough on their own, and it's clearly ahead of the next. Clearly ahead: by a margin, or by having everything the other has and more, with nothing more against it (the copy of a button with the element's own color). Two copies alike in every detail are both said ("one of these two"), three or more none: a wrong guess costs the agent more than a search.
  - **The project is read once** when `npx usepilot` starts, every file that can hold markup, however many (a vendored library filled the old 4000-file cap before nucleo-2's pages), and kept while it runs, each file read again when it changes. A search takes milliseconds.
  - **Measured, not assumed** (2026-11-23): pages rendered from labeled copies of the projects (each tag carrying its file and line, removed before Pilot describes the elements) say where every element really is. nucleo-2 (PHP, several copies of the site), 4 pages, 1303 elements: 98.5% right, 1.2% one of two, none wrong. Four static Tailwind sites, 19 pages, 1135 elements: 95% right, 2% one of two, none wrong; most of the rest are lines repeated as is in their file. Before: half of nucleo-2's answers pointed at another site's file. How to run it: [development.md](development.md), *Measuring the code search*.
- **And the project's facts** ("The project" in the prompt, [facts.ts](../packages/cli/src/facts.ts)): what the agent would otherwise work out before an edit, a step or two each, in patterns every project has, whatever it styles with.
  - **Where each changed value is set** in the project's own stylesheets ([styles.ts](../packages/cli/src/styles.ts)): the page reports the rule that sets it (its selector and `@media`), and Pilot finds that rule's line in the code. Stylesheets are read as their tools write them: Sass and Less nesting resolved (`.btn { &--primary }`), comments and mixins' templates left out, a Vue, Svelte or Astro file's `<style>`, a CSS module's hashed class back to its name (`Button_primary__a1B2c` → `.primary` in `Button.module.css`). A source wins over the CSS compiled from it (a source map, or a Sass or Less file of its name), and the rule must be in the element's own site (the nearest folder above its code with an index file or a `package.json`): never a copy in another demo or site. A rule a Sass loop or mixin generates has no line of its own (CodyHouse's `.padding-md`): nothing is said for it.
  - **What already gives the new value** (the page's part, `equivalents` in the change set, [equivalents.ts](../packages/overlay/src/dom/equivalents.ts)): the page's tokens and its single-purpose classes (`.padding-md { padding: var(--space-md) }`: a utility framework's, Bootstrap's, the project's own) that come to exactly that value now. Values are compared as the browser computes them, by a probe in Pilot's own Shadow DOM, so `24px`, `1.5rem` and a fluid `clamp()` at this width are the same; a fluid token is said to match at this width only. A token whose name says it's for another kind of property (`--text-base` for a padding) is left out.
  - **How changes reach the page on save**: a watcher that rebuilds the CSS (Tailwind's CLI, Sass, PostCSS, Less, a gulp watch) or a dev server that updates the page (Vite, Next, Astro…), from the project's scripts, so the agent doesn't build it or check the output.
  - **For a comment or a task, the element's style now and the scales to pick from** (what will change isn't known): the page sends each element's style as its CSS has it (`ElementTarget.style`, [currentStyle.ts](../packages/overlay/src/dom/currentStyle.ts)): its typography (inherited from a parent, when it doesn't set it), colors, spacing, radius, shadow, each as declared and what it comes to, and where it's set (a rule, its `style` attribute; a reset's `* { margin: 0 }` or a heading's `font-size: inherit` left out). The CLI adds each rule's line in the stylesheets, and the scales: the Tailwind theme's (letter spacing, weights, sizes, line heights, radius, families, breakpoints, the project's own colors), else the page's tokens by scale (`ChangeSet.tokens`, each at the page's width). Measured on nucleo-2 with Cursor (2026-11-23): a comment went from 10–35s and 3–11 tool calls (the agent searching the theme for the font, the weights, the tracking steps) to about 10s and one round of calls, and no made-up class (`tracking-tightest`, which Tailwind doesn't have, before).
  - **For Tailwind 4**, its theme and the class for each changed value in the project's own scale, with the width and state variants (`gap: 48px` at 768px and up → `md:gap-12`; 14px with no step of the scale → `text-[14px]`, its closest step said). Its utilities are generated, so the two parts above find nothing for them. The theme is read as Tailwind reads it: its defaults (its `theme.css` in the project's `node_modules`, else Pilot's copy of its scales), then the project's `@theme` blocks and the stylesheets they import, `--x-*: initial` clearing a namespace; of several stylesheets importing Tailwind, the one nearest the job's code. Tailwind 3 isn't read: its config is code Pilot would have to run.

  The agent still decides (the guidelines say how): the facts only spare it the looking up. Measured (2026-11-23) on CodyHouse's repository (Sass, compiled CSS beside it, many copies of its framework): of 2935 compiled rules, 92.8% found in their Sass source (the declaration's line, or the rule's when a mixin writes it), none wrong, the rest generated by loops; about 30ms each. How to run it: [development.md](development.md), *Measuring the code search*.
- **Where the time goes** is recorded per job: the hub stamps when the runner takes it and reports it done (`takenAt`, `doneAt`), the page when its check is over, and the browser console gets a line for each finished job (waiting, the agent, Pilot's check: `timings()` in [session.ts](../packages/overlay/src/bridge/session.ts)). The runner's terminal shows each job's time.
- **The follow-up:** Pilot checks the job on the page. If some changes didn't land, the same job comes back **once** as a follow-up (`followUp()` in [prompt.ts](../packages/cli/src/prompt.ts)), resuming the job's session: each change with its element, the designer's value and what the page gives, the usual causes, and "if you chose a different value on purpose, keep it and say so in your notes". After that, Pilot accepts what the code gives.

Without Pilot running for the site, nothing is sent: Send and Comment say "Pilot isn't running for this site" (*When something's stuck*). Copy prompt, which pasted the prompt into any chat, is gone (before 0.14): it could hand over edits only, while comments, tasks, questions and props need Pilot running.

## Edits: Send

The toolbar's **Send** turns the changes not sent yet into a job (`PilotSession`, [bridge/session.ts](../packages/overlay/src/bridge/session.ts)). Their preview stays on the page while the agent works, and you keep designing: new changes go in the next job.

- **Jobs in the history:** Send tags the changes not sent yet with the job's id (`EditHistory.send()`, saved with the history). Sent changes stay previewed and aren't sent again; a newer change of the same property goes in the next job. Cancel un-tags them (`unsend()`).
- **Settling:** a job's changes leave the history only through `settle()`, after the page checked them: what landed at once, what didn't after its one follow-up, and what Pilot can't check on the agent's word. A settled change leaves for good, not as an undo step: undoing it would cover the real code with a stale preview. The earlier unsent values it replaced leave with it: a property set twice before Send sends only the latest, and the first one, left behind, came back as unsent once the job landed (Send's pill still counting after the job was done). Not a Discard's copies of sent changes: they restate changes made before.

### The check after done

[edits/verify.ts](../packages/overlay/src/edits/verify.ts). For each change, the element's computed value with only the page's CSS against its computed value with the job's changes previewed (`EditHistory.probe()`, both in one task, so nothing flickers). So `1.5rem` or `pt-5` from the agent matches the designer's `20px`. Shadows match by what they draw (`sameLook()`): layers that draw nothing (fully transparent, or no offset, blur or spread) don't count, since Tailwind composes `box-shadow` from five layers and its `shadow-md` computes to four empty ones before the designer's two. Compared as text, a shadow the agent got right never matched: 15 seconds of checking, a pointless follow-up, 15 more. Lengths a pixel or two off count too (anything but shadows; 2px, and at most a quarter of the value, so 1px isn't 2px): the prompt has the agent take the project's scale when it's within a pixel or two and say so (`pr-17`, 68px, for 67px). Checked exactly, that was a difference: the reply showed at once, and the element's loader spun through the wait, a follow-up the agent answered by keeping it, and another wait.

- It checks again on every stylesheet change in the head (hot reload; Pilot's own preview sheet is ignored, `isPageMutation()`) and every half second, for up to 15 seconds. What landed is settled at once. What still differs is final sooner, once it stays so: 2 seconds after the page's stylesheets last changed, or 6 seconds from the start when they didn't change at all (hot reload usually came before the agent's "done", while its run was ending) (`QUIET`, `UNSEEN`). Waiting the whole 15 seconds, the element's loader spun that long after the agent's reply, and again after the follow-up.
- **Can't be checked, settled on the agent's word:** changes for widths other than the window's, changes for states, and elements not on this page.
- What still doesn't match after 15 seconds goes back as the follow-up, and stays previewed meanwhile (the job reads as the agent applying). After the follow-up, the job's previews go, whatever they show, so the page never stays in a state the designer has to sort out. To get an exact value the agent didn't keep, edit it again and Send: a new job.
- A finished job leaves the list shortly after (and on the next load).

## Tasks: Make responsive

**Make responsive**, one of Pilot's two in the comment box's `/` list (*The `/` menu*, below), asks the agent to make the selected element work at every viewport width.

- It goes as a job of its own (`PilotSession.request()`), apart from the changes (they wait for Send), with the words typed after it as the task's note and any files attached.
- **While a job is on the element** (that task included), it waits like a comment and goes once the job is finished, so the agent doesn't do it twice and two agents never edit the same component at once (`PilotSession.openTask()` finds an open one, by the element itself: two cards that look alike each get their own).
- **The change set** has no edits and a `request` (`ResponsiveRequest` in [types.ts](../packages/protocol/src/types.ts)): the element's target and the page's breakpoints, built by `buildRequest()` ([edits/changeSet.ts](../packages/overlay/src/edits/changeSet.ts)).
- **The prompt** (`formatPrompt()`) gives the steps: find the component and the layout around it; learn how the project does responsive (breakpoints and their names, mobile- or desktop-first, container queries); follow similar components that already have responsive rules; make the smallest changes in the project's conventions; check at a phone width, each breakpoint and just below it, and a wide desktop (horizontal scrolling, clipped text, overlaps, small tap targets), saying which widths it couldn't check; report what changed at which widths. **The steps live in the prompt rather than the skill**, so any agent (Cursor, Codex, a pasted prompt) gets them; the skill and the MCP instructions only say such jobs exist.

### Pilot's width check

[checks/widths.ts](../packages/overlay/src/checks/widths.ts), so the agent needs no screenshots.

- **Widths:** a phone width (375px), each breakpoint and 1px below it, a wide desktop (1440px) and the designer's width (`widthsToCheck()`, at most 12).
- **One hidden frame, resized** to each width in turn (media queries follow the frame's width), holding **a copy of the page as the designer has it** (`pageCopy()`): its HTML and styles (styles added through the CSSOM and adopted stylesheets written out) and its state (an open modal, classes and inline styles scripts set), without scripts (a sandboxed `srcdoc` frame), Pilot's UI or its previews (the check measures the code). Nothing runs or reloads: no analytics, requests or sockets, and heavy pages cost little. Layout that only changes through JavaScript doesn't respond in the copy, and the check's text tells the agent so (`source: "copy"`).
- **Only when the copy doesn't have the element** (inside a shadow root, say), the frame loads the page's URL instead, once (scripts on, named `pilot-probe` so Pilot doesn't mount there; `source: "load"`). This came from an outside review: loading the page once per width ran its side effects up to 12 times, and measured a fresh load instead of the designer's state.
- **Problems:** sticking out of the viewport (which side, by how much), spilling out of its parent, clipping its content, siblings overlapping; the outermost offender only. **Notes:** content scrolling sideways in a scroll container, tap targets under 24px below 768px, the page scrolling sideways because of other elements. Problems the element already has at the designer's width are left out: that width is theirs.
- Elements are labeled so the agent can find them: tag, id and `data-*`, three classes, the text inside, and `2 of 3` when siblings look alike.
- **The designer's width stays as it was:** when the task is sent, Pilot records the computed styles of the element and what's in it at the designer's width, in a frame (the code as it is), while the agent starts (`snapshotAt()`). Each check compares them again and lists what changed (`compareSnapshots()`).
- **A run works out widths from the code** (it has none of Pilot's tools: the prompt's run form), and Pilot measures after it. Until agent runs, the agent ran the check mid-job with `pilot_check_widths`: the hub sent the job's pages a `check` event, and the page that had the job ran it and posted it to `/checks/:requestId` (still in the hub, unused: for a run given Pilot's tools later).
- **Pilot runs it once more when the job is done** (after a short wait for hot reload): problems go back to the agent once as a follow-up (`issues`, `taskFollowUp()` in [prompt.ts](../packages/cli/src/prompt.ts)), resuming the job's session; after it, Pilot takes what the code gives. The loader's tooltip says "Make responsive: Queued", then the agent working, then "Checking widths".

## Basic and advanced jobs

Edits are **basic**: every value is given, so speed matters, and the job's prompt tells the agent to go straight to the code with no screenshots, builds or tests (Pilot checks the page). Tasks like Make responsive and Break and fix are **advanced**: they need judgment, so their prompt says so and asks the agent to hand them to a more capable model than its own, if it can (a subagent, or another model it offers). No vendor or model is named: the chat's own model stays the designer's choice. A fast one keeps edits quick, and advanced tasks still get a strong one where the agent allows it.

**Every job says what code it wants**, for every agent alike: the values are the designer's intent, not code, to be written as production code in the project's own styling system, whatever it is (Tailwind, CSS or Sass modules, StyleX, vanilla-extract, Panda, styled-components, a component library's props…), following how the element's component is styled already, with its tokens, without inline styles or `!important` (`DESIGN_INTENT`, `PROJECT_CODE` in [format.ts](../packages/protocol/src/format.ts)).

## Comments

The toolbar's **Comment** tool picks elements like Select, but the selected one gets the **comment widget** ([CommentWidget](../packages/overlay/src/ui/components/CommentWidget/CommentWidget.tsx)) instead of the property dialog, placed by the same rules (`dialogSpot`, `dialogPosition`, `raisedSpot`; draggable by its top strip), with the same selection actions. Editing and commenting stay separate tools (other main actions will come, like Screenshot). The widget is the owner's design.

- **A thread per element** (`CommentThread` in [session.ts](../packages/overlay/src/bridge/session.ts), saved in the tab's sessionStorage like the jobs, found again after a reload, see *Finding elements again*): the designer's comments and the agent's replies.
- **On several elements:** with several selected ([page.md](page.md), *Several elements*), a comment, or a task asked from the box, is about all of them: one job (`others` beside `target` in the request, `requestTargets()` in [types.ts](../packages/protocol/src/types.ts)), whose prompt lists each element. The thread, its icon and the box are on the first one; the job's loader shows on every one, and it waits while a job is on any of them. The thread remembers what was selected when the designer last wrote in it (`CommentThread.others`): opening it selects them all again, and its next message goes to all of them. Writing in it with fewer selected makes it about those from then on. For a shared component, the prompt has the agent change it only when every copy on the page is selected, and ask otherwise. A task's width check measures the first element only, for now (checking each would multiply the frames); the prompt tells the agent to read the code for the others.
- **Replies are rendered as markdown**, the subset agents write ([markdown.tsx](../packages/overlay/src/ui/components/CommentWidget/markdown.tsx): paragraphs, bold, italic, inline code, fenced code, lists; headings as bold paragraphs). Web addresses are links, underlined in the text's color, as a Markdown link or written out (a dev server's address an agent gives, `http://localhost:5188/states/button/`): http and https only, anything else (`javascript:`) stays text, opened in a new tab with nothing passed back to the page (`rel="noopener noreferrer"`). It builds elements, never HTML, so a reply can't inject anything.
- **Replies are concise by design:** the comment prompt and the run's footer ask for a chat message: what changed, an answer, or what the agent needs, in a few short sentences at most, no headings. It's a small chat box for quick design back-and-forth, not a report. A comment with a skill is the exception (*Skills*, below).
- **The thread** scrolls past a height, opens at its latest message and stays there while its content settles (fonts loading, a reply arriving) unless the designer scrolled up. Pilot's scroll thumb and edge fades, each shown only while there's more that way.
- **While the latest comment isn't answered**, where it stands shows as the reply to come, in the reply's bubble, with a band sweeping along its text: "Waiting for an agent…", "Claude Code is working on it…" (the agent's name, without its project), "Queued…". The real reply replaces it.
- **Sent right away** (`PilotSession.comment()`): each comment is a job of its own (a `CommentRequest`: the element, the thread so far with the new comment last, the page's breakpoints), its prompt built by `formatComment()` ([format.ts](../packages/protocol/src/format.ts)). Comments go to an agent only: without one, send is disabled and says "No agent connected".
- **The editor's edits go with it.** Edits made with Select on the selected elements, not sent yet, go with the comment (`takesEdits` on the message, `postComment()` in [session.ts](../packages/overlay/src/bridge/session.ts)): the designer tweaks the padding, switches to Comment and writes "like this, on mobile too", and the agent needs both. The box shows them as a chip ("2 changes", styled like the action chips; placeholder wording), on by default; taking it off leaves them for Send. One job: the prompt lists them after the comment, with their values, to apply exactly (`formatComment()` in [format.ts](../packages/protocol/src/format.ts)), and Pilot checks them when the agent is done as it checks Send's, with one follow-up for what didn't land; the agent's notes are the reply. **Where the comment and an edit disagree on a property, the comment wins**: it was written after the edit (`COMMENT_WINS` in [format.ts](../packages/protocol/src/format.ts)), and the follow-up Pilot sends for the edit's value tells the agent to keep what the comment asked. Found on the bench lab (2026-11-24): an edit set `margin-bottom: var(--spacing)`, the comment said "10× the spacing variable", and the follow-up made the agent switch `mb-10` back to `mb-1`. The follow-up still costs a round; rejected for now: the agent naming the properties it overrode, so Pilot checks them on its word (a new field through the hub and the page). Other elements' edits stay for Send. Not with a `/` action: a task goes apart from the changes. Sent, the thread shows how many went as words, in green ("2 changes"): chips are only for the comment being written.
- **The agent's notes are its reply:** the run's reply (without its `pilot` block) joins the thread ("Done." without notes), and the next comment carries them. Nothing to check (free text): done on the agent's word.
- **Edit manually:** the latest reply to a job has a button, **Edit manually** (the owner's wording; first "Adjust"; the look of a question's secondary answer), that switches to Select with the thread's elements selected, so the property dialog opens on them: the designer tweaks what the agent chose ("make the text bigger" → the font size it picked) where the width chip and the state pills reach what a comment can't. Only under a reply whose job changed how the thread's elements look, as far as the dialog edits it (`ThreadMessage.restyled`): when a comment or task is sent, Pilot notes its elements' computed values for every property the dialog's editors write, with the page's own CSS ([edits/look.ts](../packages/overlay/src/edits/look.ts)); after the reply it compares them with the page's every half second for up to 10 seconds, as hot reload brings the code in (`watchLook()`), and marks the reply at the first difference, so the button can come a moment after the reply, never go. A reply that changed nothing (an answer), or only what the dialog can't edit (an icon swapped for one of the same size, text, props) has none: the owner found it under a Nucleo icon swap, where it made no sense. Not on a question either (its answers are there), a `/props` list, or "Stopped". Rejected: the changed properties as editable rows under the reply (found by comparing the CSS before and after the job): it couldn't hold other widths or states, which the dialog already handles. Adjusting doesn't answer the thread: it still needs the designer until they reply or resolve it.
- **The agent decides** how to take it: a specific ask is done right away, like an edit; an open-ended one is an advanced task; a question gets an answer and no change.
- **Stop:** while the thread's latest job is with the agent and can still be taken back, a stop button sits left of send (the attach button's look): it cancels the job, as the loader's × does. Stopped either way, the thread says so where the reply would be, in the agent's bubble though Pilot writes it ("Stopped. Write again to pick it up.", `stopped` on the message): not a reply to read (no comment icon, no count), and in the thread the agent reads next, it says the job was stopped and may not be done, so it isn't taken as done.
- **Drafts are kept:** what's being written stays with its element for the tab ([drafts.ts](../packages/overlay/src/ui/drafts.ts), found again as threads are): close the box (Esc, a click elsewhere), come back or reload, and it's there; sending clears it.
- **Sent, the box closes:** the element's loader says it's with the agent, and the reply comes back to the thread (its icon, the toolbar's count). A send that fails keeps the box and the draft, with a red reply saying why; a one-click answer closes it too, unless a draft is being written.
- **Keys:** Enter sends, Option+Enter resolves, Esc closes; Shift+Enter is a new line. While typing a comment, Cmd/Ctrl+Z undoes the text, and Alt+D types.
- **Resolving** (Mark as solved, or Option+Enter) removes the thread and throws a short confetti burst from the button ([Confetti](../packages/overlay/src/ui/components/Confetti/Confetti.tsx), drawn by App as the widget closes; none with reduced motion).
- **Attachments:** the attach button picks images, text files (txt, md, csv, json, log) and PDFs, several at once, or they're dropped anywhere on the comment box: while files are over it, a blurred layer covers it with "Drop to attach" (the owner's design); the box takes the drop, so the browser doesn't open the file instead. They preview above the field (images as themselves, other files as a tile with their extension, a placeholder look), each removable. A comment can be attachments alone: they may hold the instructions (a screenshot, a sketch, notes, a spec), and the prompt tells the agent to ask in its reply if they're unclear. On send, the page uploads each file to the hub (`POST /attachments`, same origin check as jobs), which saves it in the **OS temp folder** ([attachments.ts](../packages/cli/src/attachments.ts)): never in the project, so nothing to commit or ship; named by content, so a resend is one file; cleared after a week when a hub starts, and by the system in time. The hub checks each file is what its type says (an image's or a PDF's signature; text as UTF-8 with no NUL bytes), and nothing ever serves, opens or runs them. The job names files by id only, and the hub adds each path when it takes the job, so a page can't point the agent at another file. A run gets the new comments' text files' contents in its prompt, and images by path (Claude Code may read the attachments' folder, `--add-dir`; Codex gets them with `-i`); PDFs (and files too big to send inline) are opened from the path the prompt lists. The thread keeps a small preview of each image, for the designer. If an upload fails, nothing is sent and the draft stays.

### The `/` menu

Typing `/` at the start of any word in the comment box lists the designer's **skills** (*Skills*, below), after Pilot's own two: **Props**, on a component's instance only (*Props*, below), and **Make responsive** (above), as one list ([actions.ts](../packages/overlay/src/ui/components/CommentWidget/actions.ts)), filtered as you type, like the property search's modifiers (↑/↓, Enter or Tab picks, Esc closes the list and leaves the text). Not inside a word, so "and/or" and URLs stay text; and the list only shows when something matches, so a `/about` is just text and Enter sends it. Picked, it's a chip at the start of the message and its `/word` leaves the text (Backspace at the start removes the chip); one per message. The rest of the words and any files go with it, and it can be sent alone. While the `/` or `@` list is open, the attach and send buttons hide: picking is the next step.

- **Skills first** (the owner's call, 2026-11-24): the designer's skills, their team's own workflows kept with their code, are what sets Pilot apart, and every agent runs them the same way. Pilot's own two read as skills made by Pilot; the rest of Pilot's tasks (Break and fix) and the previews of what was planned (Fit its container, Check accessibility, Explore variations, Use design tokens, Add states, Support dark mode, Add motion, listed but doing nothing) left the menu. Break and fix's code stays (`TaskRequest`), unused.
- **Pilot's two are jobs of their own** (`TaskRequest`, `PropsRequest` in [types.ts](../packages/protocol/src/types.ts)), shown in the thread as the designer's message (`action` on the message), `/responsive` in green, before the words; the agent's notes come back as its reply. Props first on a component's instance: it's what that selection is most likely for.
- **Rows in the actions' design** (the owner's pick): the name, with the description under it (two lines at most: a skill's can be long), and **who made it** in the top-right corner: Pilot for Pilot's two, a skill's author when its `SKILL.md` says one (`author`, or `metadata.author` as the Agent Skills format keeps it: `ProjectSkill.author`, read by [skills.ts](../packages/cli/src/skills.ts)), nothing otherwise. Not the `@` list's design (its group heading, the name and description on one line), which the skills had before.

### Skills

The `/` list is the designer's **skills**: the ones their agent's own `/` shows (made by them, or installed from others, `npx skills add …`), after Pilot's own two. Picking one makes it a chip; the comment then goes as usual, with the elements, its words, files, mentions and the edits that go with a comment, and the agent uses that skill for it. Sent, the thread shows it as typed, `/better-ui` in green, before the words.

- **Pilot lists them, the agent runs them.** Pilot's process reads each skill's `SKILL.md` for its name and description ([skills.ts](../packages/cli/src/skills.ts)), from the folders the agent Pilot runs reads them from (`skills` in `AGENTS`, [agents.ts](../packages/cli/src/agents.ts)): the project's (its folder and each above it, up to the repository's root), first, then the user's. A skill installed only for another agent isn't listed, as that agent's own `/` wouldn't list it. Read again each time the list opens, so a skill installed meanwhile shows. The page gets names and descriptions only (`POST /skills`, same origin check as the others): where they are stays with the hub: the runner tells it only which agent it runs (`AgentInfo.kind`, kept with `folder`), and the hub works the folders out. Not the folders themselves: a hub from an older Pilot, which doesn't know to keep a new field to itself, would pass them on to pages.
- **The run starts with the skill**, as the designer would start it in the agent's chat: `/name` in Claude Code and Cursor, `$name` in Codex (`invokeSkill`), the prompt's first line, for the comment that picked it only (not its follow-up or an answer, which resume the session that used it; `skillOf()` in [run.ts](../packages/cli/src/run.ts)). Explicit, so a skill only its user may start (`disable-model-invocation: true`, as `variant` or `break` in some collections) starts too: picking it is the designer starting it. Every agent's prompt also says it (`formatComment()` in [format.ts](../packages/protocol/src/format.ts)): use the skill, it wins over Pilot's guidelines where they differ, skip and say what the run can't do, and say so if there's no such skill.
- **Pilot doesn't control what a skill does**: that's the agent's job, in the run's permissions (*Agent runs*). A skill that needs a browser, a script or the web does it if the designer allowed it in their agent, and says it couldn't otherwise. Checked like a comment: on the agent's word, its reply in the thread, Edit manually after.
- **Reading a skill's other files:** Pilot doesn't read or send them; the agent opens them as it does in its chat. Claude Code's chat would ask before reading them in the home folder, which a run can't answer, so its runs may read `~/.claude/skills` (read-only: `--allowedTools 'Read(~/.claude/skills/**)'`; it still can't edit them). Codex and Cursor read them as they run.
- **Rejected:** Pilot reading the skill and putting it in the prompt (so no agent needs access to where it is): the agent loads skills better itself (its other files when it needs them, its own rules for them), and it's how the designer uses them in the chat. Tested on macOS (2026-11-21) with a skill in the home folder, one in the project, and one only its user may start, for each agent: all three run them.
- **A few at once:** the list shows the best few matches, and typing narrows them, as the `@` list's few per group.
- **Its look is the owner's pick:** the chip and the rows are the actions' (*The `/` menu*).
- **The reply is the skill's:** a comment's reply is concise, like a chat message; with a skill, it's as the skill says to report (findings, options), as long as it needs (the thread renders Markdown and scrolls), and the run's rules about not opening a browser or running builds are left to the skill too (`skillOf()` in [prompt.ts](../packages/cli/src/prompt.ts)).
- **Not listed: a Claude Code plugin's skills** (`plugin:skill`): Claude Code's alone (Pilot lists what every agent has the same way), in its own plugin storage, which may change; the usual ways to get a skill (`npx skills add`, a folder copied, your own) land in the folders Pilot reads. Worth adding if designers ask.

### Mentions (@)

Typing `@` at the start of a word, anywhere in a message, lists what the designer can mention, so they name it instead of describing it ("use `--color-brand` like `@ProductCard`"): the page's **tokens**, its **components** and its **named elements**, in groups, filtered as they type (without case or the `--`/`@` prefixes; a token's value matches too, `#1cf69e`), a few per group. ↑/↓, Enter or Tab picks, as in the `/` list; Esc closes the list and leaves the text as typed. An `@` inside a word (an email) isn't one.

- **What's listed** is read from the page each time the list opens, never stored ([dom/mentions.ts](../packages/overlay/src/dom/mentions.ts)), so a token or component added in the code shows after hot reload. It's read as the list opens, in the same render, so Enter or Tab pressed right after `@x` picks instead of sending.
  - **Tokens:** the project's file tokens too (*Variables*, [property-dialog.md](property-dialog.md)), by their own names (`color.brand.primary`, `$brand`), the agent told their file; and the CSS variables the stylesheets define on the root (`:root`, `html`, `:host`, also inside `@layer` and `@media`), with their value now ([dom/tokens.ts](../packages/overlay/src/dom/tokens.ts)): Tailwind v4's `@theme`, shadcn/ui, Open Props and most design systems put theirs there. Tailwind's `--tw-*` plumbing and Pilot's preview sheet are left out; colors show a swatch. Tokens that only live in code (a `tokens.json`, a Tailwind v3 config) can't be read from the page: the hub will read those files ([design-tokens.md](design-tokens.md)).
  - **Components:** the page's, each by its name as the hover label shows it (*Components*, [page.md](page.md)), once; then the **project's**, the ones the page doesn't render (on another page, or not used yet), with their folder. Pilot's process in the project reads those from the code (`POST /components`, [components.ts](../packages/cli/src/components.ts)), so they're there only while it runs for the page: exported React components (functions, arrows, `forwardRef`, `memo`), Vue and Svelte files; not helpers used in one file, hooks, route files (`page.tsx`), tests or stories. It reads from the workspace's root (a monorepo's, so `packages/ui` is there for its app), never above the repository. Kept current without a watcher: each time the list opens it walks the folders again and reads only files saved since (milliseconds: about 25ms for a thousand files, 200ms the first time), so a component an agent or the designer adds shows the next time. A watcher was rejected: it behaves differently per OS, must follow new folders, and costs while Pilot runs, for what a walk on open covers. A component made by a factory of the project's own (`motion.create(Card)`) isn't found: typed, the agent looks for it.
  - **Elements:** the ones with a name of their own, an id or a naming attribute (`section#features`, `button[data-testid=buy]`). Plain tags (`div`) aren't listed: there are too many, and they name nothing.
- **Picked, it goes into the text as it reads:** a token by its name (`--color-brand`), a component or an element after `@` (`@ProductCard`, `@section#features`), with a space. The message also carries it as a **reference** (`CommentReference` in [types.ts](../packages/protocol/src/types.ts)): a token with its value, a component with one of its instances on the page (and its file), an element as Pilot describes a target. Only picks still in the text when it's sent go (one deleted from the text is dropped). **Typed, not picked, it counts too** (`mentionsIn()` in [mentions.ts](../packages/overlay/src/ui/components/CommentWidget/mentions.ts)): an `@name` that names a listed thing (without case, when only one matches; trailing punctuation and `'s` aren't part of it) becomes its reference, a `--token` the page defines too; an `@name` found nowhere goes as **unlisted**, for the agent to look for.
- **The agent reads each as it reads in the comment, then what it is and where** (`referenceLine()` in [format.ts](../packages/protocol/src/format.ts)), so it can go straight to the code: "`@ProductCard`: the `ProductCard` component, declared in `src/ProductCard.tsx:5`; one of its instances on the page: `article.card`". A file and line are the best hint an agent can get; without them, what to search for (`function X`, `const X =`, a `X.vue` file). Picked ones are exact ("use them, don't look for others"), a token as `var(--x)` or the project's form of it; an unlisted one is "probably a component or a part of the page: search the project, ask if unclear". Before the agent gets the job, its own server fills in what the page couldn't (`withComponentFiles()` in [locate.ts](../packages/cli/src/locate.ts)): a project component's file relative to the agent's folder (the list's are relative to the workspace's root), and a component or unlisted name with no file, by its declaration, across the workspace. With a `/` action, they go in the task with its note. An answer to the agent's question is words only, for now.
- **In the thread**, a sent message's mentions show apart from its words (placeholder look, pending the design).

### Props

`/props`, offered when the selection is one component's instance (its top-level element, as the hover label names it), lets the designer change it through its props, from a list, instead of describing it ("make it the dark one").

- **Pilot reads the instance's props itself**, from the framework in development (`componentProps()` in [dom/component.ts](../packages/overlay/src/dom/component.ts)): React's fiber (`memoizedProps`, from the copy on screen: the one a DOM node points at can be the one from before the last render), Vue's instance (`props`). Strings, numbers and on-off values only; not handlers, children, class names or styles. Also where the instance is written (its parent's file). Not for Server Components: their props stay on the server.
- **What it can be set to lives in the code** (a union type, a cva or tailwind-variants config, a Vue `validator`), so a job asks the agent (`formatProps()` in [format.ts](../packages/protocol/src/format.ts)): read the component, change nothing, and return the props that change how it looks in its reply's `pilot` block (`props`) (`PropSpec`: options, on-off, text or number, the values it accepts, the default). Any model can do it: it's a basic job. The hub keeps them on the job (`propsOf()` checks them), and the page shows them as the agent's reply.
- **In the thread, a bullet per prop, inside the agent's reply** ([PropsList](../packages/overlay/src/ui/components/PropsList/PropsList.tsx)), in its words' style: the name as code, the instance's value on the page (else the default), then what it takes, dimmed: the agent's description (a number's range, a text's form: the prompt asks for them), else the values (`sm, md or lg`, `true or false`), else `a number`, `text`. Under them, dimmed, how to change one, from the first prop, its line in full contrast: "Reply `tone: dark` to change one." The agent's sentence doesn't describe them (the prompt says Pilot lists them). **Why** (the owner's call, 2026-11-25): first a box of the property dialog's fields under the reply (a select per option, a field per text or number, on the darkest background), a pick writing the line. Fields invite a preview the page can't give (a prop is code: see *No preview*), and right inputs (a wheel for a range, a color picker for a class) would need more from the agent and a preview to mean anything; a panel beside the thread, like a shadow's, was considered and dropped for the same reason.
- **Changing one is a line in the reply**, `name: value` (`tone: dark`), typed by the designer ([propLines.ts](../packages/overlay/src/ui/components/CommentWidget/propLines.ts)). Words: the comment reads as the designer wrote it, and the agent, who listed the props, reads it as such. Sent, Pilot reads back the lines that name a listed prop with a value it takes (`propsInText()`), so the job carries them exact (`props` on the message: the component, where it's written, from → to) and Pilot checks them: the agent sets them where the instance is written, not in the component, and asks first when that line renders several instances (a loop over data) or the value comes from data. Not with a `/` action.
- **No preview:** a prop isn't CSS, so the page changes once the agent edited the code and hot reload ran (a few seconds). Rejected: re-rendering the instance with the new props from the overlay (it would reach into the framework's internals, and what shows wouldn't be the code).
- **Checked like an edit:** once the agent is done, Pilot reads the instance's props again, every 400ms for up to 6s (hot reload takes longer in some frameworks), compared as text. What isn't what the designer picked goes back once as a follow-up (`taskFollowUp()` in [prompt.ts](../packages/cli/src/prompt.ts)); after it, Pilot takes what the code gives.
- **Answered, the list stays** with the agent's words (nothing in it to pick), its values the page's now. `/props` again for a new list.
- **Remembered, never stale:** each component's list is kept for the tab (by name and file). The next `/props` on it shows it at once, while the agent reads the code again; its reply updates that same message, so new props show and gone ones go, and lines already typed stay (they're in the comment). Shown early, it isn't a reply to read: the thread counts it once the agent's in.
- **Not yet:** for one instance at a time.

### Tasks: Break and fix

Not offered since 2026-11-24 (the owner's call: *The `/` menu*): its code stays, unused.

`/break` asks the agent to stress-test the element with odd but realistic content (text far longer or shorter than the placeholder, long words like URLs, missing optional parts, many items, images in odd shapes or failing to load) and fix what breaks without changing its usual look: truncation or line clamps where text is cut, `min-width: 0` and `flex-shrink: 0` where flex squeezes the wrong items, wrapping, `object-fit` / `background-size` with a fixed frame ratio and a fallback for images. A distorted image keeps its box, so Pilot's check can't see it: the prompt has the agent read the code for it. The agent works out from the code where odd content would break it (trying content temporarily if it helps), fixes, and puts the real content back. Pilot checks it after like Make responsive, with the usual content: the designer-width comparison watches layout and type, not overflow or `min-width`, so fixes pass as long as the usual look holds, and test content left in the code shows up as a change there.

### The agent asks

When part of a job needs the designer's decision, the agent asks instead of guessing, and doesn't wait for the answer. The case it's made for is **shared code changed in only some copies**: the designer restyled one card, the cards come from one component, and the edit is for every card or a variation of this one.

**A comment that's unclear, or asks for what the element already is** ("make this square": square corners, or a 1:1 shape?) gets a question at once, in the agent's reply (`UNCLEAR_ASK` in [format.ts](../packages/protocol/src/format.ts)): one short sentence naming the options, nothing changed for that part, and what the designer meant is looked for in the comment, its elements and the code only, never git history, other agent sessions or the web. **Why** (2026-11-24, the bench lab, Cursor): "make this square" on a tile already `aspect-square` took 17 model rounds and 127s (git refused five times, other sessions' transcripts, a web search) before a question, about scope, that wasn't the doubt; a comment that was clear took 2 rounds. In the reply, not the `pilot` block: a job asks that one once, and the shared-code question may still be needed after the answer, which comes back as the designer's next comment in the thread (its session resumed). Rejected: one question with both (meaning and scope) as choices, too many to fit on one line.

- **Pilot says how many look-alikes each element has**: the elements like it on the page that the job leaves out (`lookAlikes` on the target, from the same search as Select similar, [page.md](page.md)), and, in a React or Vue app, which component they're instances of (`lookAlikesOf`, with the element's component and file in `source`: [page.md](page.md), *Components*). The prompt gives the count; the agent tells from the code whether they share it. Every job's guidelines say when to ask (`sharedCode()` in [format.ts](../packages/protocol/src/format.ts)): only when they share it and not every copy is in the job.
- **The agent does the rest of the job, leaves that part, and asks** in its reply's `pilot` block (`question`: one short sentence and up to four one-click `choices`). Its other jobs go on.
- **Three answers for shared code, with one meaning for every agent** (`SHARED_CHOICES` in [format.ts](../packages/protocol/src/format.ts)), the agent's suggestion first: **All of them** changes the component itself; **Only this** changes it where this instance is used, with what the component already accepts (classes through its `className`, merged the project's way, or one of its props), else the smallest pass-through, never a variant or inline styles; **New variant** adds a named option the way the component defines variants (`cva`, a `variant` prop) and uses it here. Why three: in component code "only this one" is two different things, a one-off at the call site or a reusable option, and only the designer knows which they mean, while the agent knows what the code allows. The labels are short so the three fit on one line. The answered job spells out what the chosen one asks (`sharedChoiceMeaning()`), so it doesn't depend on the agent remembering the guidelines.
- **No question when the answer is known:** the designer said it (in the comment or note: "only here", "every card", "as a variant"), or nothing else uses that code.
- **Every copy in the job** (Select similar, or each one picked: `everyCopy` on the target, set when the search finds no look-alike left out) says the scope, the owner's call (2026-11-25): **a component's instances** (`everyCopy.of`, React, Vue) mean the component, so the agent changes it in its own file, reaching wherever it's used, other pages too, never a variant, and doesn't ask; **copies matched by the page's structure** (plain HTML, no component) mean every one on this page only, and if the only way is code other pages share (a global stylesheet's class, a partial), the agent asks first with the three answers. Why: picking every instance of a component is the clearest way a designer says "the component", while plain HTML's copies may be markup repeated by hand, and Pilot sees only the page it's on. Worked out from the selection, not the button, so picking them all by hand means the same; taking one out afterwards brings back the look-alikes and the question. Before, "every copy is in the job" only meant "don't ask", which left the scope (each instance, the component, a variant) to the agent.
- **Pilot asks it in a comment thread** on the element it's about: the job's own thread (a comment's), else that element's thread, else a new one about it (`PilotSession.ask()`). On a job about several elements the question names one, by its number in the prompt (`AgentQuestion.element`; the run's footer asks for it only then): a Send with a card and a footer link once asked about the link on the card's thread, the job's first element. Naming none (it's about all of them), the first element, and a new thread is about all of them. The choices are buttons under the question, the first (the agent's suggestion: it lists it first) the more prominent; the designer can also write an answer. The thread needs them (see below), and the job shows no loader meanwhile, on its elements or in the toolbar's jobs button: the question says where it stands, and the loader is back once it's answered.
- **The job is held, not checked:** its previews stay, since what the agent left isn't in the code yet, after a reload too (it was checked then, and its follow-up went to the agent with the question skipped). **It holds nothing back** (`holds()` in [session.ts](../packages/overlay/src/bridge/session.ts)): no agent is on it, so a comment or a Send on its elements goes at once. Then what it already landed there settles (`settleLanded()` in [verify.ts](../packages/overlay/src/edits/verify.ts)), so the new job's code can't later show as a difference in its check and get a follow-up undoing it; a change the designer makes again replaces the job's anyway. An answer given while another job is on its elements waits for that one (`answerWaits`, not posted to the hub until then), as a comment would. **Why** (2026-11-24): a comment on a features grid, with its edits, said "Queued" and never went: the grid was in an earlier Send whose agent had asked about a badge elsewhere on the page, and nothing said the comment was waiting for that answer.
- **The answer** (a choice, or the designer's next message in that thread) sends the job back to the agent, preferably the one that asked (`POST /jobs/:id/answer`, `Hub.answer()`), with the question and the answer (`answered()` in [prompt.ts](../packages/cli/src/prompt.ts)), resuming the session that asked. When it's done again, Pilot checks it like any job, and the agent's notes are its reply in the thread. A job asks once: a second question is dropped, and the agent says what's still open in its notes. So when a job changes some copies of several shared components, the prompt says to ask one question naming them all ("Every **PlanCard** and **FeatureCard**, or only the ones you changed?") and apply the answer to each: asked about the plan cards only, an agent once applied the feature cards' edits to the edited cards alone, and the cards came out mixed.
- **Why not block:** waiting for the answer would hold up the agent's other jobs, and the designer may answer much later. Why not apply first and ask after: undoing a variation to change the component (or the other way) is more work than asking first.

### Threads that need you

A thread needs you when the agent spoke last. Replying sends it back to the agent, resolving removes it, opening it changes nothing (`PilotSession.attention`, `needsYou()`).

- **Every unresolved thread shows on its element**, with either tool: its outline, and a **comment icon** on its top-right corner that opens the thread (switching to Comment). While its latest comment is with the agent, the loader shows instead. No numbered pins: the icons mark the threads. It stays at the far right of the corner; the selection's actions and a job's loader sit on its left.
- **The Comment button** gets a pill with how many need you ("2 comments to review"). While Comment is on, each click opens the next one, oldest first, wrapping around, scrolled into view and flashed (threads on other pages skipped). Esc closes the widget and drops the selection; the next Esc turns the tool off.

## Closing

Close, the toolbar's last button, closes Pilot on the whole site: `POST /quit` (the page's own origin only), and the hub sends the site's pages a `quit` event (its other tabs close). Nothing else: jobs go on (Pilot keeps running the agent for them, and checks them when it's open again), and the shortcut opens it again. Since agent runs there's no chat to release: until then Quit also ended the agents' waits, so their chats stopped the loop. Details in [page.md](page.md), *Launching and quitting*.

## When something's stuck

Pilot never leaves a loader spinning with no clue why. A job nothing will move by itself is **stuck**, and the page says what's wrong and what to do (`PilotSession.stuck`, [session.ts](../packages/overlay/src/bridge/session.ts)):

- **A run failed** (`agent-error`): Pilot couldn't run the agent for a job (not installed, not signed in, the run failed). Said at once, with the run's own title and what to do (*Agent runs*, *Errors*), until the designer sends again or cancels the job.
- **A run has gone quiet** (`quiet`): the agent hasn't shown any work for 2 minutes (`QUIET_MS`): its service stalled (Codex's once waited 14 minutes before its first step). "Claude Code has gone quiet · No sign of work for 2 minutes. Click to stop it, then send again." The runner reads the agent's output as it comes and tells the hub (`activityOf()` in [run.ts](../packages/cli/src/run.ts), at once and at most every 15s), which keeps the job's last activity (`Job.activeAt`); the page looks again when a run would turn quiet, so it's said by itself, and goes when work shows again. Agents print every few seconds as they work (each tool call; Claude Code as it thinks too, with `--include-partial-messages`), so a long task that's working is never said quiet. A run from a runner that doesn't report it is never said quiet.
- **Pilot isn't running for this site** (`offline`, `no-agent`): the page can't reach the hub, or reaches it but nothing runs for its site: "Restart your dev server if Pilot starts with it, or run npx usepilot in your project's folder".
- **The agent isn't ready** (`setup`): Pilot runs for the site, but its agent isn't installed or signed in (*Before the agent is ready*): "Sign in to Claude Code", "Claude Code isn't installed", "Signing in to Claude Code", with what to do. Said with jobs or without, on Comment and Send both, like Pilot not running: whatever goes next waits.
- **An older Pilot is running** (`older-agent`): the page can't reach its hub, but an older version's answers on its port (4747 + an older bridge version, newest first; `olderHub()` in [client.ts](../packages/overlay/src/bridge/client.ts), at most every 10s, only on the default address): an agent's chat on the MCP loop, or an older `npx usepilot`, which can't reach this page. Said with jobs or without, on Comment and Send both, as "Pilot isn't running for this site" with the same command. The page can't read the answer (no-cors), only that something's there: another app on one of those ports would say it too, a rare case taken for the clue it gives.

Each is said only once it has lasted (past a reconnect; a failed or quiet run at once), and goes by itself when it's solved. One is said at a time: Pilot not running first (it stops every job: an earlier failure mustn't hide it, or the jobs still open would spin with nothing said), then a quiet run, then a failed one (its thread says it either way). Until agent runs, "isn't listening" said when no chat had asked for a job for a while: there's no chat to listen now. Not stuck: a job queued behind one an agent is on, a question waiting for the designer's answer, a job being checked. An agent that leaves mid-job (its chat closed) isn't a stuck state either: the hub puts its jobs back in the queue (`Hub.unregister`), for another chat or the same one back. A long task that's working isn't called stuck: its tooltip says how long the agent has been on it ("· 12 min"); a quiet one is (above).

Where it shows, the owner's design: the toolbar's pill turns red with "!", its tooltip the message on two lines (wrapping past 240px: an agent's error can be long): on Comment and Send both when an older Pilot is running (whatever goes next can't reach Pilot), else on the button the stuck jobs belong to (Comment for comments and tasks asked in a thread, Send for the rest: a failed run, a quiet one); the elements' corner loader gives way to a red warning (still), its tooltip the same, and hovering still turns it into an X that cancels the job; the element's fill stops breathing, and the jobs button goes when every job is stuck (none is being worked on); in the thread, the reply to come becomes a red reply. A send that fails (an attachment that didn't upload) is a red reply too, and the draft stays.

## Elements being worked on

A job that isn't finished (waiting, an agent on it, being checked, its follow-up), but one waiting for the designer's answer (below), is **on elements**: a task's or a comment's element, the elements an edits job changes (`PilotSession.jobOn()`, `busy`; found again by selector after a reload).

- **It shows**, selected or not, while Pilot runs: the element keeps its outline, its fill breathes (opacity only, so it runs on the compositor; still with reduced motion), and a **loader** takes its top-right corner ([SelectionActions](../packages/overlay/src/ui/components/SelectionActions/SelectionActions.tsx) `busy`), a stepped rotation so the graphics card turns it alone. Its tooltip says what the job is about, then where it stands: the comment's own words (“Make the price bigger”, with the edits that went with it), the task (Make responsive, Props of ProductCard), or the edits by what they are ("3 style changes", "1 text change": changes are always said with their kind, `changesLabel()`). On the page, a thread whose job is with the agent shows only the loader: the comment icon means a reply to read, and showing it all the time would lose that. Selected, its icon sits beside the loader, the selection's own action, to open the thread and see the whole conversation. The loader is always the far-right icon, with its tooltip hanging left (clear of the panel beside the element); its × on hover is Nucleo's xmark. Placeholder look, pending design.
- **Cancel is on the loader:** hovering it turns it into an X while the agent isn't done, and a click takes the job back ("Cancel job"; a job on several elements is cancelled whole).
- **No second job goes to it.** Send leaves its changes out: they **wait**, and go as a job of their own once the job on it is finished (`held` in [session.ts](../packages/overlay/src/bridge/session.ts), saved by selector). So two agents, or the agent's edit and the designer's next one, never cross on one element. Only the changes of the elements that waited go then, not edits made meanwhile elsewhere. Send's tooltip says "Queued" (or "Sent; some queued"), and Send stays dimmed while all that's unsent waits. A cancelled job doesn't release what waited for it: its own changes are unsent again, and everything goes with the next Send.
- **Comments wait too.** One written while a job is on the element shows in the thread at once, says "Queued", and goes once the job is finished, with any others that waited, as one job carrying the whole thread (`waiting` on the message). The agent couldn't read it mid-job anyway (a run reads its prompt once), and this way a second run can't take it and edit the same code meanwhile, nor can its change land while Pilot is still checking the job before (which would send a follow-up undoing it). A comment's own job counts too: the next comment on that element waits for the agent's reply. Unlike held changes, waiting comments also go when the job is cancelled.

**The job list** ([JobList](../packages/overlay/src/ui/components/JobList/JobList.tsx)) isn't shown for now: what a history of the session should hold is open (what changed, before → after; how it landed; the files touched; a summary to copy). Its `statusText` and `whatText` give the loaders' tooltips.

## The hub

[packages/cli](../packages/cli): [hub.ts](../packages/cli/src/hub.ts), [server.ts](../packages/cli/src/server.ts), [agent.ts](../packages/cli/src/agent.ts), [run.ts](../packages/cli/src/run.ts).

- **One per machine and bridge version**, on `127.0.0.1:` 4747 + `BRIDGE_VERSION` (4754 for version 7, agent runs; `PILOT_PORT` overrides it). Projects on the same version share it; a project on another version runs its own, so two versions never block each other on one port (before 0.7.0, every version used 4747). It lives in the first process that runs Pilot (a dev server with Pilot in it, or `npx usepilot`); later ones get `EADDRINUSE`, check `/health`, and talk to it over HTTP (`/agents/*`). When the hub's process ends (its chat closed), the next call of another agent fails to connect and that process takes over the port.
- **State is in memory only.** The page posts its unfinished jobs again on every connect, and the hub must accept a job posted again (idempotent by id), so a takeover loses nothing.
- Remote agents ping regularly and are dropped after missing a few.
- **Versions:** every process checks the hub's bridge version (`/health`, `BRIDGE_VERSION` in `@pilot/protocol`) and refuses to join one of another version (7 since agent runs: a job's `session` and `error`, `/agents/job`, quit closing pages only; 9 since Pilot runs before its agent is ready: an agent's `setup`, `/setup/sign-in`, `/agents/setup`). With a port per version, that only happens when `PILOT_PORT` puts two versions on one port; the message says so.
- **Follow-ups:** `POST /jobs/:id/retry` puts a done job back in the queue once (`attempt: 2`, with its `differences`), given first to the agent that did it if it's waiting (`Hub.retry()`).
- **Routing:** jobs are filed by page origin (`localhost`, `127.0.0.1` and `[::1]` count as the same, `originKey()`): an agent only gets jobs from the page it launched for. Two repos open at once stay separate. The runner takes up to five jobs at once, so the designer can run tasks in parallel (`dispatch()` in [hub.ts](../packages/cli/src/hub.ts) gives each to a free slot), and an element with a job on it holds the next one, so two runs never edit it at once.
- **Security:** the page's origin comes from the `Origin` header, never from the request body; jobs are only accepted from an origin Pilot runs for (`npx usepilot` or the dev server registers it), so another website can't hand prompts to the agent. Agent routes refuse any request with an `Origin` (browsers send one, Node doesn't). Keep both checks for every new route. `POST /setup/sign-in` has both: only a page Pilot runs for can ask, it starts the agent's own sign-in command and nothing else, and only for an agent that waits for one (`Hub.requestSignIn()`, taken once by its runner through `/agents/setup`).
- **An agent not ready yet** registers with its `setup` (above), checked by the hub before pages see it (`setupOf()`); the hub tells the pages again whenever an agent's label or setup changes.
- **The project's folder** (`AgentInfo.folder`, the runner's project folder) goes to the hub with the agent, for `POST /components`: the hub keeps it to itself, and what it sends pages (the agents, `launch`, jobs) never has it.

## The page side

### Finding elements again

Threads, jobs and the edit history are saved per tab and find their elements again after a reload (`findTarget()` in [dom/target.ts](../packages/overlay/src/dom/target.ts)). The selector Pilot saved has the element's classes, and those change: a prop sets a variant (`card--light` → `card--dark`), the agent edits a class. So:

1. **Its selector**, when the element it finds has the saved text (two cards that swapped classes would otherwise trade threads).
2. **Else where it is**, by tags and positions only (`at`: `#react > main > div > article:nth-of-type(1)`, from the nearest id), with its text or its component (a prop may have changed the text too).
3. **Else its path without classes**, for what was saved before `at`: the one element there with its text and component.
4. **Else its selector's element** (its text was changed on purpose), or none: a wrong element would be worse than none.
