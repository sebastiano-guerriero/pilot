# Agent handoff

The handoff is **jobs**. Edits, tasks (Make responsive) and comments each go to the agent as a job; the agent applies it; Pilot checks the result on the page. The page is the source of truth for its jobs.

```
page (your app in dev, the overlay)          one hub per machine and version, 127.0.0.1:4754
  Send ──POST /jobs──────────────────────▶  ┌───────────────────────────────────┐
  job updates, launch ◀──SSE /events───────  │ jobs and runners, by page origin  │
  follow-up ──POST /jobs/:id/retry───────▶  └───────────────────────────────────┘
                                               ▲ in-process            ▲ HTTP
                                 `npx usepilot` in project A   `npx usepilot` in project B
                                 (runs the hub)                (joins it, takes over if A stops)
                                       │ one run per job, the prompt on stdin
                                       ▼
                                 claude -p · codex exec · cursor-agent -p
```

## Agent runs

**Pilot runs the agent itself, once per job** ([run.ts](../packages/cli/src/run.ts), [agents.ts](../packages/cli/src/agents.ts)). `npx usepilot`, in the project's folder beside the dev server, joins (or hosts) the hub, registers for the site, and for each job starts the agent's command-line tool in the project's folder: the prompt on stdin, its JSON output read for the reply and the session. Nothing waits in an agent's chat.

**Why** (2026-11-20). The first design parked an agent's chat inside an MCP tool call (`pilot_wait_for_edits`), and it couldn't be made reliable: Cursor caps a turn at 25 tool calls and pauses it (every few Sends the designer had to find the chat and press Resume), MCP clients time idle calls out, a chat had to stay open and listening, and a comment thread's follow-up went to whichever chat was free, without the context of the first. Running the agent per job has none of that: every Send works, whenever. Tested on macOS with Claude Code, Codex and Cursor, on a test page and on nucleo-2 (8,000 files): edit jobs in 10–25s, comments in 15–35s, two jobs at once in the same file both landed.

- **Agents:** Claude Code (`claude -p`), Codex (`codex exec`), Cursor (`cursor-agent -p`). Each is an entry in `AGENTS`: its executables, how to install it and sign in, its sign-in check, its flags, and how to read its output. Gemini (`gemini -p`), Copilot (`copilot -p`) and opencode (`opencode run`) have the same three things (one task and exit, a session id, resume by id), by their own help: not added yet.
- **The agent:** `--agent`, else the one saved for the project folder (in `~/.config/usepilot/projects.json`, never in the repo: a teammate may use another). `init` saves the agent whose chat runs it (`agentFromEnv()`: the setup prompt runs inside the agent, which its environment tells), so `npx usepilot` normally doesn't ask. With none saved, the only one signed in; with several, it asks once in the terminal (the owner's call: detection first, a simple question as the fallback). Each sign-in check takes about a second.
- **The site: the page says its project.** Each page's loader names its project (`mountPilot({ project })`, its package.json's `name`, written by `init`: `loaderCall()` in [init.ts](../packages/cli/src/init.ts)); the page sends it with `/events?project=`, and `npx usepilot` takes only a page with its own project's name (`projectName()` in [config.ts](../packages/cli/src/config.ts)), whatever its address, so a teammate on another port works too. It never takes another project's page: each one it sees and leaves is said once in the terminal, with why ("open on … for *playground*, not *nucleo*"; "its loader doesn't say which project it is: … update"), and the page's toolbar names its project ("Pilot isn't running for *shop*"), or says its loader names none. `--url` skips the check. **Why** (2026-11-21): taking the first local page with Pilot open picked the Pilot playground open in another tab instead of nucleo-2. Rejected: asking in the terminal (the owner didn't want it), the agent writing the dev address down at setup (breaks when the address changes, or a teammate opens it another way), and recognizing the page from its files and texts (a heuristic).
- **Permissions: the agent's own, as in its chat** (checked by [scripts/agent-runs-check.mjs](../scripts/agent-runs-check.mjs) on macOS, and on Windows and Linux by the **Agent runs** workflow). A run can do what the designer allowed that agent (its settings, allow rules, MCP servers, skills), and edit the project's files, which is the job; what its chat would ask about is refused, since no one is there to answer, and the agent says so in its reply. Never a flag that skips permissions. Claude Code runs with the designer's settings in `acceptEdits` (`-p` refuses what would prompt: checked, so not `--permission-prompts none`, which older versions don't know). Codex runs in its sandbox in the mode its chat uses for a project (`-s workspace-write`: writes in the project and the OS temp folder, which `git` needs), the rest from the designer's config (network, web search, rules); `exec` never asks. Cursor runs in its allowlist mode (`--sandbox disabled`, never `--force`): what the designer's allowlist doesn't allow is refused. Not its sandbox: it doesn't exist on Windows ("requires macOS or Linux"), and on Linux it fails on Ubuntu's default AppArmor settings (it needs unprivileged user namespaces); found by the Agent runs workflow, where both modes passed every check once the sandbox could start. **On Windows**, Codex's sandbox needs a mode or every run is read-only (every command "blocked by policy"): `windows.sandbox="unelevated"`, which needs no admin rights; both modes passed on GitHub's Windows machines.
  - **Why** (2026-11-21). Pilot is a different way to ask the designer's agent, not an agent of its own, so a run does what the chat does: no more, no less. Until then each run had Pilot's own limits (the project's files only, no shell, no internet: Claude Code `--restricted` with five file tools, Codex's web search off), stricter than the chat: "make my footer like Linear's" couldn't look at Linear's site, and skills that need a tool couldn't work. Rejected: skipping permissions (`--dangerously-skip-permissions`, `--force`) so nothing is refused: no one watches a run, and part of a prompt isn't the designer's (the page's text, attachments, a skill someone else wrote), so an instruction hidden there would run unchecked. Next: the agent's permission requests asked in the thread, with Allow and Deny, as in the chat (Claude Code has `--permission-prompt-tool`; not every agent has a way yet).
- **The prompt goes on stdin**, never as an argument: no quoting or length limits on Windows (npm's `.cmd` shims need a shell; their arguments are only Pilot's flags, session ids and paths). It's the job's prompt in its run form (`run: true` in `formatPrompt()`, through `jobPrompt()`): the guidelines in full (a fresh run hasn't read them), the reply is the notes, a question or a props list goes in a fenced `pilot` block at its end (JSON, read by `replyOf()`), and tasks work out widths from the code: Pilot measures them after the run and sends problems back once (the follow-up it always had). The text files attached come in the prompt; images by path (Claude Code may read the attachments' folder, `--add-dir`; Codex gets them with `-i`).
- **Sessions:** a job done carries its agent session (`Job.session`, `{ agent, id }`). Its follow-up and the answer to its question resume it; a comment thread keeps the last one (`CommentThread.session`) and its next message resumes it, so the agent remembers the thread. Only the same agent's session is resumed, and only a plain id (letters, digits, dashes: `sessionOf()`, since it becomes an argument). A session that's gone costs nothing: every comment carries its whole thread, and a run that fails without a reply runs once more without the session.
- **Errors:** a run that fails reports the job done with an `error` (title, what to do): "Claude Code isn't signed in · Run claude auth login in a terminal, then send again", or "couldn't do this job" with the first line of what it said (the terminal has the rest). A failed run is tried once more first (Cursor once returned nothing in half a second), except a sign-in problem. The page says it at once where stuck jobs are (*When something's stuck*), and the job's changes are unsent again, still previewed, for the next Send.
- **At once:** up to three jobs run together (`SLOTS`); the page never sends two on one element at once (*Elements being worked on*). Stop (the loader's X) cancels the job, and the runner, which checks every 2s, kills the run.
- **The terminal** shows one line per job (what it is, then the time and the reply's first line, or what went wrong). Ctrl+C stops Pilot.
- **Speed:** each agent step costs 3–4s (a model round trip), so a job is about as fast as the steps it needs: the code's location Pilot finds (*The loop*) and the edit guidelines' "no screenshots, builds or tests" matter as much here. Measured, and what's next, in the roadmap.

Until agent runs (0.13 and earlier), an agent's chat ran Pilot: `/pilot` called `pilot_launch`, then waited for jobs in `pilot_wait_for_edits` and reported each with `pilot_done`, on Pilot's MCP server. It's gone; `usepilot mcp` remains only to tell an old setup what to do.

## Installing

The user installs their agent's command-line tool and signs in (once per machine, the README's table), then pastes one prompt into their agent: run `npx usepilot@latest init` and follow what it prints ([init.ts](../packages/cli/src/init.ts)). The user never edits code by hand:

- **The command does what must be exact:** it installs `usepilot` as a dev dependency with the project's package manager (from the lockfile, up to the repository's root), checks the agents' command-line tools (`detectAgents()`: installed, signed in) and says which Pilot will run or what to install or sign in to (`--agent` saves one for the project), and removes Pilot's old chat setup wherever it finds it ([legacy.ts](../packages/cli/src/legacy.ts): its MCP server in each agent's config, the `/pilot` skill, from before agent runs; only Pilot's entries and files). Nothing is added to the repo. Run again, it changes nothing.
- **The agent does what needs judgment:** the command detects the framework (Vite, Next.js App and Pages Router, Nuxt, SvelteKit, Astro, React Router, webpack) and prints the snippet that loads Pilot in development only, and where; the agent writes it the project's way. A site with no bundler Pilot knows (PHP, Rails, Django, plain HTML) gets one tag in the shared layout, printed only when Pilot's own file is on disk (a dev dependency, never deployed: the agent checks the deploy rules, or asks) **and** the project's own development setting says so; never from the request (the Host header and the client's IP can say anything behind a proxy, or from a client). **Pilot never runs in production**, whatever the loader: `mountPilot` does nothing on a page that isn't on a development address (`isLocalHost()` in [bridge.ts](../packages/protocol/src/bridge.ts): this machine, local names like `*.test` or `nucleo`, private networks), not even its shortcut. An app that loads Pilot already gets no such step. It names a file only when it found it, and otherwise says what to look for: a guessed path that doesn't exist sends the agent searching. A Vite app whose pages load no module of their own (classic scripts) may deploy its HTML as it is, without Vite building it, so its HTML isn't touched: Pilot is injected from the Vite config by a plugin that only runs while Vite serves (`apply: "serve"`, `transformIndexHtml` before Vite's own processing, so the package resolves).
- **The agent tells the user** to run `npx usepilot` in the project's folder, beside the dev server, and open the app.
- A monorepo's root gets the list of its apps instead, to run it in the right one.

### Updating

`npx usepilot@latest update`, in the app's folder ([update.ts](../packages/cli/src/update.ts)). It installs the latest `usepilot` with the project's package manager, removes Pilot's old chat setup (as `init` does), and prints the version change and what's left, for a designer to read as much as for an agent: restart the app's dev server (its bundler keeps the old Pilot until then) and `npx usepilot`, and, when the bridge version changed (read from the old bundle before it's replaced), update the other projects too.

- **Why a command of its own:** `init` is setup, safe to run any time, and never changes a version you have (as `shadcn init` and `prisma init` don't); upgrading is a deliberate step, as with `storybook upgrade`. `init` on a project with an older Pilot leaves it alone and says that `update` updates it.
- **An old chat setup that's still there** (a project not updated, an agent's config `init` couldn't edit) starts `usepilot mcp`, which now only says, in the agent's MCP log, to run `update` and `npx usepilot`.

## Finding the code, and the time

- **Pilot finds the code first.** The runner runs in the project's folder, so before it hands over a job it searches the project's source files for each element (its id, text, classes and tag, nearby lines counting, `node_modules` and builds skipped, under a second in all; first in its component's file when the page named the component, which it finds by name when the page couldn't name the file: [page.md](page.md), *Components*) and adds where the code probably is, with the lines around it ([locate.ts](../packages/cli/src/locate.ts)). The agent can go straight to the edit instead of searching. It's only said when a line is clearly the element (its id or text, or most of several classes): a wrong guess costs the agent a look. Found wrong on nucleo-2, a repository with several sites: text that only contains the element's text matched another site's file (the roadmap's *Speed* item).
- **Where the time goes** is recorded per job: the hub stamps when the runner takes it and reports it done (`takenAt`, `doneAt`), the page when its check is over, and the browser console gets a line for each finished job (waiting, the agent, Pilot's check: `timings()` in [session.ts](../packages/overlay/src/bridge/session.ts)). The runner's terminal shows each job's time.
- **The follow-up:** Pilot checks the job on the page. If some changes didn't land, the same job comes back **once** as a follow-up (`followUp()` in [prompt.ts](../packages/cli/src/prompt.ts)), resuming the job's session: each change with its element, the designer's value and what the page gives, the usual causes, and "if you chose a different value on purpose, keep it and say so in your notes". After that, Pilot accepts what the code gives.

Without Pilot running for the site, nothing is sent: Send and Comment say "Pilot isn't running for this site" (*When something's stuck*). Copy prompt, which pasted the prompt into any chat, is gone (before 0.14): it could hand over edits only, while comments, tasks, questions and props need Pilot running.

## Edits: Send

The toolbar's **Send** turns the changes not sent yet into a job (`PilotSession`, [bridge/session.ts](../packages/overlay/src/bridge/session.ts)). Their preview stays on the page while the agent works, and you keep designing: new changes go in the next job.

- **Jobs in the history:** Send tags the changes not sent yet with the job's id (`EditHistory.send()`, saved with the history). Sent changes stay previewed and aren't sent again; a newer change of the same property goes in the next job. Cancel un-tags them (`unsend()`).
- **Settling:** a job's changes leave the history only through `settle()`, after the page checked them: what landed at once, what didn't after its one follow-up, and what Pilot can't check on the agent's word. A settled change leaves for good, not as an undo step: undoing it would cover the real code with a stale preview.

### The check after done

[edits/verify.ts](../packages/overlay/src/edits/verify.ts). For each change, the element's computed value with only the page's CSS against its computed value with the job's changes previewed (`EditHistory.probe()`, both in one task, so nothing flickers). So `1.5rem` or `pt-5` from the agent matches the designer's `20px`.

- It checks again on every stylesheet change in the head (hot reload; Pilot's own preview sheet is ignored, `isPageMutation()`) and every half second, for up to 15 seconds. What landed is settled at once.
- **Can't be checked, settled on the agent's word:** changes for widths other than the window's, changes for states, and elements not on this page.
- What still doesn't match after 15 seconds goes back as the follow-up, and stays previewed meanwhile (the job reads as the agent applying). After the follow-up, the job's previews go, whatever they show, so the page never stays in a state the designer has to sort out. To get an exact value the agent didn't keep, edit it again and Send: a new job.
- A finished job leaves the list shortly after (and on the next load).

## Tasks: Make responsive

**Make responsive**, a `/` action in the comment box (*Actions*, below), asks the agent to make the selected element work at every viewport width.

- It goes as a job of its own (`PilotSession.request()`), apart from the changes (they wait for Send), with the words typed after it as the task's note and any files attached.
- **While a job is on the element** (that task included), it waits like a comment and goes once the job is finished, so the agent doesn't do it twice and two agents never edit the same component at once (`PilotSession.openTask()` finds an open one, by the element itself: two cards that look alike each get their own).
- **The change set** has no edits and a `request` (`ResponsiveRequest` in [types.ts](../packages/protocol/src/types.ts)): the element's target and the page's breakpoints, built by `buildRequest()` ([edits/changeSet.ts](../packages/overlay/src/edits/changeSet.ts)).
- **The prompt** (`formatPrompt()`) gives the steps: find the component and the layout around it; learn how the project does responsive (breakpoints and their names, mobile- or desktop-first, container queries); follow similar components that already have responsive rules; make the smallest changes in the project's conventions; check at a phone width, each breakpoint and just below it, and a wide desktop (horizontal scrolling, clipped text, overlaps, small tap targets), saying which widths it couldn't check; report what changed at which widths. **The steps live in the prompt rather than the skill**, so any agent (Cursor, Codex, a pasted prompt) gets them; the skill and the MCP instructions only say such jobs exist.

### Pilot's width check

[checks/widths.ts](../packages/overlay/src/checks/widths.ts), so the agent needs no screenshots.

- **Widths:** a phone width (375px), each breakpoint and 1px below it, a wide desktop (1440px) and the designer's width (`widthsToCheck()`, at most 12).
- **One hidden frame, resized** to each width in turn (media queries follow the frame's width), holding **a copy of the page as the designer has it** (`pageCopy()`): its HTML and styles (styles added through the CSSOM and adopted stylesheets written out) and its state (an open modal, classes and inline styles scripts set), without scripts (a sandboxed `srcdoc` frame), Pilot's UI or its previews (the check measures the code). Nothing runs or reloads: no analytics, requests or sockets, and heavy pages cost little. Layout that only changes through JavaScript doesn't respond in the copy, and the check's text tells the agent so (`source: "copy"`).
- **Only when the copy doesn't have the element** (inside a shadow root, say), the frame loads the page's URL instead, once (scripts on, named `pilot-probe` so Pilot doesn't mount there; `source: "load"`). This came from an outside review: loading the page once per width ran its side effects up to 12 times, and measured a fresh load instead of the designer's state.
- **Problems:** sticking out of the viewport (which side, by how much), spilling out of its parent, clipping its content, siblings overlapping; the outermost offender only. **Notes:** content scrolling sideways in a scroll container, tap targets under 24px below 768px, the page scrolling sideways because of other elements. Problems the element already has at the designer's width are left out: that width is theirs.
- Elements are labeled so the agent can find them: tag, id and `data-*`, three classes, the text inside, and `2 of 3` when siblings look alike.
- **The designer's width stays as it was:** when the task is sent, Pilot records the computed styles of the element and what's in it at the designer's width, in a frame (the code as it is), while the agent starts (`snapshotAt()`). Each check compares them again and lists what changed (`compareSnapshots()`).
- **A run works out widths from the code** (it has none of Pilot's tools: the prompt's run form), and Pilot measures after it. Until agent runs, the agent ran the check mid-job with `pilot_check_widths`: the hub sent the job's pages a `check` event, and the page that had the job ran it and posted it to `/checks/:requestId` (still in the hub, unused: for a run given Pilot's tools later).
- **Pilot runs it once more when the job is done** (after a short wait for hot reload): problems go back to the agent once as a follow-up (`issues`, `taskFollowUp()` in [prompt.ts](../packages/cli/src/prompt.ts)), resuming the job's session; after it, Pilot takes what the code gives. The loader's tooltip says "Make responsive: Queued", then the agent working, then "Checking widths".

## Basic and advanced jobs

Edits are **basic**: every value is given, so speed matters, and the job's prompt tells the agent to go straight to the code with no screenshots, builds or tests (Pilot checks the page). Tasks like Make responsive and Break and fix are **advanced**: they need judgment, so their prompt says so and asks the agent to hand them to a more capable model than its own, if it can (a subagent, or another model it offers). No vendor or model is named: the chat's own model stays the designer's choice. A fast one keeps edits quick, and advanced tasks still get a strong one where the agent allows it.

**Every job says what code it wants**, for every agent alike: the values are the designer's intent, not code, to be written as production code in the project's own styling system, whatever it is (Tailwind, CSS or Sass modules, StyleX, vanilla-extract, Panda, styled-components, a component library's props…), following how the element's component is styled already, with its tokens, without inline styles or `!important` (`DESIGN_INTENT`, `PROJECT_CODE` in [format.ts](../packages/protocol/src/format.ts)).

## Comments

The toolbar's **Comment** tool picks elements like Select, but the selected one gets the **comment widget** ([CommentWidget](../packages/overlay/src/ui/components/CommentWidget/CommentWidget.tsx)) instead of the property dialog, placed by the same rules (`dialogSpot`, `dialogPosition`, `raisedSpot`; draggable by its top strip), with the same selection actions. Editing and commenting stay separate tools (other main actions will come, like Screenshot). The widget is the owner's design.

- **A thread per element** (`CommentThread` in [session.ts](../packages/overlay/src/bridge/session.ts), saved in the tab's sessionStorage like the jobs, found again after a reload, see *Finding elements again*): the designer's comments and the agent's replies.
- **On several elements:** with several selected ([page.md](page.md), *Several elements*), a comment, or a task asked from the box, is about all of them: one job (`others` beside `target` in the request, `requestTargets()` in [types.ts](../packages/protocol/src/types.ts)), whose prompt lists each element. The thread, its icon and the box are on the first one; the job's loader shows on every one, and it waits while a job is on any of them. The thread remembers what was selected when the designer last wrote in it (`CommentThread.others`): opening it selects them all again, and its next message goes to all of them. Writing in it with fewer selected makes it about those from then on. For a shared component, the prompt has the agent change it only when every copy on the page is selected, and ask otherwise. A task's width check measures the first element only, for now (checking each would multiply the frames); the prompt tells the agent to read the code for the others.
- **Replies are rendered as markdown**, the subset agents write ([markdown.tsx](../packages/overlay/src/ui/components/CommentWidget/markdown.tsx): paragraphs, bold, italic, inline code, fenced code, lists; headings as bold paragraphs, links as their text). It builds elements, never HTML, so a reply can't inject anything.
- **Replies are concise by design:** the comment prompt and the run's footer ask for a chat message: what changed, an answer, or what the agent needs, in a few short sentences at most, no headings. It's a small chat box for quick design back-and-forth, not a report. A comment with a skill is the exception (*Skills*, below).
- **The thread** scrolls past a height, opens at its latest message and stays there while its content settles (fonts loading, a reply arriving) unless the designer scrolled up. Pilot's scroll thumb and edge fades, each shown only while there's more that way.
- **While the latest comment isn't answered**, where it stands shows as the reply to come, in the reply's bubble, with a band sweeping along its text: "Waiting for an agent…", "Claude Code is working on it…" (the agent's name, without its project), "Queued…". The real reply replaces it.
- **Sent right away** (`PilotSession.comment()`): each comment is a job of its own (a `CommentRequest`: the element, the thread so far with the new comment last, the page's breakpoints), its prompt built by `formatComment()` ([format.ts](../packages/protocol/src/format.ts)). Comments go to an agent only: without one, send is disabled and says "No agent connected".
- **The editor's edits go with it.** Edits made with Select on the selected elements, not sent yet, go with the comment (`takesEdits` on the message, `postComment()` in [session.ts](../packages/overlay/src/bridge/session.ts)): the designer tweaks the padding, switches to Comment and writes "like this, on mobile too", and the agent needs both. The box shows them as a chip ("2 changes", styled like the action chips; placeholder wording), on by default; taking it off leaves them for Send. One job: the prompt lists them after the comment, with their values, to apply exactly (`formatComment()` in [format.ts](../packages/protocol/src/format.ts)), and Pilot checks them when the agent is done as it checks Send's, with one follow-up for what didn't land; the agent's notes are the reply. Other elements' edits stay for Send. Not with a `/` action: a task goes apart from the changes. Sent, the thread shows how many went as words, in green ("2 changes"): chips are only for the comment being written.
- **The agent's notes are its reply:** the run's reply (without its `pilot` block) joins the thread ("Done." without notes), and the next comment carries them. Nothing to check (free text): done on the agent's word.
- **Adjust:** the latest reply to a job has a button, **Adjust** (the look of a question's secondary answer), that switches to Select with the thread's elements selected, so the property dialog opens on them: the designer tweaks what the agent chose ("make the text bigger" → the font size it picked) where the width chip and the state pills reach what a comment can't. Not on a question (its answers are there), a `/props` list, or "Stopped". Rejected: the changed properties as editable rows under the reply (found by comparing the CSS before and after the job): it couldn't hold other widths or states, which the dialog already handles. Adjusting doesn't answer the thread: it still needs the designer until they reply or resolve it.
- **The agent decides** how to take it: a specific ask is done right away, like an edit; an open-ended one is an advanced task; a question gets an answer and no change.
- **Stop:** while the thread's latest job is with the agent and can still be taken back, a stop button sits left of send (the attach button's look): it cancels the job, as the loader's × does. Stopped either way, the thread says so where the reply would be, in the agent's bubble though Pilot writes it ("Stopped. Write again to pick it up.", `stopped` on the message): not a reply to read (no comment icon, no count), and in the thread the agent reads next, it says the job was stopped and may not be done, so it isn't taken as done.
- **Drafts are kept:** what's being written stays with its element for the tab ([drafts.ts](../packages/overlay/src/ui/drafts.ts), found again as threads are): close the box (Esc, a click elsewhere), come back or reload, and it's there; sending clears it.
- **Sent, the box closes:** the element's loader says it's with the agent, and the reply comes back to the thread (its icon, the toolbar's count). A send that fails keeps the box and the draft, with a red reply saying why; a one-click answer closes it too, unless a draft is being written.
- **Keys:** Enter sends, Option+Enter resolves, Esc closes; Shift+Enter is a new line. While typing a comment, Cmd/Ctrl+Z undoes the text, and Alt+D types.
- **Resolving** (Mark as solved, or Option+Enter) removes the thread and throws a short confetti burst from the button ([Confetti](../packages/overlay/src/ui/components/Confetti/Confetti.tsx), drawn by App as the widget closes; none with reduced motion).
- **Attachments:** the attach button picks images, text files (txt, md, csv, json, log) and PDFs, several at once, or they're dropped anywhere on the comment box: while files are over it, a blurred layer covers it with "Drop to attach" (the owner's design); the box takes the drop, so the browser doesn't open the file instead. They preview above the field (images as themselves, other files as a tile with their extension, a placeholder look), each removable. A comment can be attachments alone: they may hold the instructions (a screenshot, a sketch, notes, a spec), and the prompt tells the agent to ask in its reply if they're unclear. On send, the page uploads each file to the hub (`POST /attachments`, same origin check as jobs), which saves it in the **OS temp folder** ([attachments.ts](../packages/cli/src/attachments.ts)): never in the project, so nothing to commit or ship; named by content, so a resend is one file; cleared after a week when a hub starts, and by the system in time. The hub checks each file is what its type says (an image's or a PDF's signature; text as UTF-8 with no NUL bytes), and nothing ever serves, opens or runs them. The job names files by id only, and the hub adds each path when it takes the job, so a page can't point the agent at another file. A run gets the new comments' text files' contents in its prompt, and images by path (Claude Code may read the attachments' folder, `--add-dir`; Codex gets them with `-i`); PDFs (and files too big to send inline) are opened from the path the prompt lists. The thread keeps a small preview of each image, for the designer. If an upload fails, nothing is sent and the draft stays.

### Actions

Tasks for the agent about the element live in the comment box, not on the selection's corner: typing `/` at the start of any word lists them ([actions.ts](../packages/overlay/src/ui/components/CommentWidget/actions.ts)), filtered as you type, like the property search's modifiers (↑/↓, Enter or Tab picks, Esc closes the list and leaves the text). Not inside a word, so "and/or" and URLs stay text; and the list only shows when an action or one of the agent's skills matches (*Skills*, below), so a `/about` is just text and Enter sends it. (It used to open only at the start of the message, which made the designer start over to add one.) The corner has room for a few icons; a list can grow. Picked, an action is a chip at the start of the message and its `/word` leaves the text (Backspace at the start removes the chip); one per message. The rest of the words and any files go with it, and it can be sent alone. While the `/` or `@` list is open, the attach and send buttons hide: picking is the next step.

- **It's the designer's message in the thread** (`action` on the message), sent as the task's job instead of a comment. The chip is only for writing: sent, the thread shows the action as typed, `/responsive` in green, before the words. The thread shows where it stands as for a comment (and "Checking every width" while Pilot checks a Make responsive), and the agent's notes come back as its reply, so the designer can answer it.
- **Make responsive**, **Break and fix** and **Props** (*Props*, below) so far; each new one is an entry in the list and a kind of request (`TaskRequest`, `PropsRequest` in [types.ts](../packages/protocol/src/types.ts)). An action can be offered only for some selections (`forComponent`: Props, for a component's instance alone, and listed first then: it's what that selection is most likely for). **Previews** (`preview` in [actions.ts](../packages/overlay/src/ui/components/CommentWidget/actions.ts)) are listed but not built: shown in the menu like the others (the owner's video, and a look at what's coming), but picking one does nothing, so nothing unbuilt reaches an agent: Fit its container (container queries), Check accessibility, Explore variations, Use design tokens, Add states, Support dark mode, Add motion. Building one makes it a kind of request, and drops `preview`.

### Skills

The `/` list also has the designer's **skills**: the ones their agent's own `/` shows (made by them, or installed from others, `npx skills add …`), listed after Pilot's actions under a heading of their own. Picking one makes it a chip, like an action; the comment then goes as usual, with the elements, its words, files, mentions and the edits that go with a comment, and the agent uses that skill for it. Sent, the thread shows it as typed, `/better-ui` in green, before the words.

- **Pilot lists them, the agent runs them.** Pilot's process reads each skill's `SKILL.md` for its name and description ([skills.ts](../packages/cli/src/skills.ts)), from the folders the agent Pilot runs reads them from (`skills` in `AGENTS`, [agents.ts](../packages/cli/src/agents.ts)): the project's (its folder and each above it, up to the repository's root), first, then the user's. A skill installed only for another agent isn't listed, as that agent's own `/` wouldn't list it. Read again each time the list opens, so a skill installed meanwhile shows. The page gets names and descriptions only (`POST /skills`, same origin check as the others): where they are stays with the hub: the runner tells it only which agent it runs (`AgentInfo.kind`, kept with `folder`), and the hub works the folders out. Not the folders themselves: a hub from an older Pilot, which doesn't know to keep a new field to itself, would pass them on to pages.
- **The run starts with the skill**, as the designer would start it in the agent's chat: `/name` in Claude Code and Cursor, `$name` in Codex (`invokeSkill`), the prompt's first line, for the comment that picked it only (not its follow-up or an answer, which resume the session that used it; `skillOf()` in [run.ts](../packages/cli/src/run.ts)). Explicit, so a skill only its user may start (`disable-model-invocation: true`, as `variant` or `break` in some collections) starts too: picking it is the designer starting it. Every agent's prompt also says it (`formatComment()` in [format.ts](../packages/protocol/src/format.ts)): use the skill, it wins over Pilot's guidelines where they differ, skip and say what the run can't do, and say so if there's no such skill.
- **Pilot doesn't control what a skill does**: that's the agent's job, in the run's permissions (*Agent runs*). A skill that needs a browser, a script or the web does it if the designer allowed it in their agent, and says it couldn't otherwise. Checked like a comment: on the agent's word, its reply in the thread, Adjust after.
- **Reading a skill's other files:** Pilot doesn't read or send them; the agent opens them as it does in its chat. Claude Code's chat would ask before reading them in the home folder, which a run can't answer, so its runs may read `~/.claude/skills` (read-only: `--allowedTools 'Read(~/.claude/skills/**)'`; it still can't edit them). Codex and Cursor read them as they run.
- **Rejected:** Pilot reading the skill and putting it in the prompt (so no agent needs access to where it is): the agent loads skills better itself (its other files when it needs them, its own rules for them), and it's how the designer uses them in the chat. Tested on macOS (2026-11-21) with a skill in the home folder, one in the project, and one only its user may start, for each agent: all three run them.
- **A few at once:** the list shows the best few matches, and typing narrows them, as the `@` list's few per group.
- **Its look is the owner's pick:** the chip is an action's; the group is the `@` list's: its heading, and rows on one line, the name and the description cut at its right, as a token's name and value.
- **The reply is the skill's:** a comment's reply is concise, like a chat message; with a skill, it's as the skill says to report (findings, options), as long as it needs (the thread renders Markdown and scrolls), and the run's rules about not opening a browser or running builds are left to the skill too (`skillOf()` in [prompt.ts](../packages/cli/src/prompt.ts)).
- **Not listed: a Claude Code plugin's skills** (`plugin:skill`): Claude Code's alone (Pilot lists what every agent has the same way), in its own plugin storage, which may change; the usual ways to get a skill (`npx skills add`, a folder copied, your own) land in the folders Pilot reads. Worth adding if designers ask.

### Mentions (@)

Typing `@` at the start of a word, anywhere in a message, lists what the designer can mention, so they name it instead of describing it ("use `--color-brand` like `@ProductCard`"): the page's **tokens**, its **components** and its **named elements**, in groups, filtered as they type (without case or the `--`/`@` prefixes; a token's value matches too, `#1cf69e`), a few per group. ↑/↓, Enter or Tab picks, as in the `/` list; Esc closes the list and leaves the text as typed. An `@` inside a word (an email) isn't one.

- **What's listed** is read from the page each time the list opens, never stored ([dom/mentions.ts](../packages/overlay/src/dom/mentions.ts)), so a token or component added in the code shows after hot reload. It's read as the list opens, in the same render, so Enter or Tab pressed right after `@x` picks instead of sending.
  - **Tokens:** the project's file tokens too (*Variables*, [property-dialog.md](property-dialog.md)), by their own names (`color.brand.primary`, `$brand`), the agent told their file; and the CSS variables the stylesheets define on the root (`:root`, `html`, `:host`, also inside `@layer` and `@media`), with their value now ([dom/tokens.ts](../packages/overlay/src/dom/tokens.ts)): Tailwind v4's `@theme`, shadcn/ui, Open Props and most design systems put theirs there. Tailwind's `--tw-*` plumbing and Pilot's preview sheet are left out; colors show a swatch. Tokens that only live in code (a `tokens.json`, a Tailwind v3 config) can't be read from the page: the hub will read those files ([design-tokens.md](design-tokens.md)).
  - **Components:** the page's, each by its name as the hover label shows it (*Components*, [page.md](page.md)), once; then the **project's**, the ones the page doesn't render (on another page, or not used yet), with their folder. Pilot's process in the project reads those from the code (`POST /components`, [components.ts](../packages/cli/src/components.ts)), so they're there only while it runs for the page: exported React components (functions, arrows, `forwardRef`, `memo`), Vue and Svelte files; not helpers used in one file, hooks, route files (`page.tsx`), tests or stories. It reads from the workspace's root (a monorepo's, so `packages/ui` is there for its app), never above the repository. Kept current without a watcher: each time the list opens it walks the folders again and reads only files saved since (milliseconds: about 25ms for a thousand files, 200ms the first time), so a component an agent or the designer adds shows the next time. A watcher was rejected: it behaves differently per OS, must follow new folders, and costs while Pilot runs, for what a walk on open covers. A component made by a factory of the project's own (`motion.create(Card)`) isn't found: typed, the agent looks for it.
  - **Elements:** the ones with a name of their own, an id or a naming attribute (`section#features`, `button[data-testid=buy]`). Plain tags (`div`) aren't listed: there are too many, and they name nothing.
- **Picked, it goes into the text as it reads:** a token by its name (`--color-brand`), a component or an element after `@` (`@ProductCard`, `@section#features`), with a space. The message also carries it as a **reference** (`CommentReference` in [types.ts](../packages/protocol/src/types.ts)): a token with its value, a component with one of its instances on the page (and its file), an element as Pilot describes a target. Only picks still in the text when it's sent go (one deleted from the text is dropped). **Typed, not picked, it counts too** (`mentionsIn()` in [mentions.ts](../packages/overlay/src/ui/components/CommentWidget/mentions.ts)): an `@name` that names a listed thing (without case, when only one matches; trailing punctuation and `'s` aren't part of it) becomes its reference, a `--token` the page defines too; an `@name` found nowhere goes as **unlisted**, for the agent to look for.
- **The agent reads each as it reads in the comment, then what it is and where** (`referenceLine()` in [format.ts](../packages/protocol/src/format.ts)), so it can go straight to the code: "`@ProductCard`: the `ProductCard` component, declared in `src/ProductCard.tsx:5`; one of its instances on the page: `article.card`". A file and line are the best hint an agent can get; without them, what to search for (`function X`, `const X =`, a `X.vue` file). Picked ones are exact ("use them, don't look for others"), a token as `var(--x)` or the project's form of it; an unlisted one is "probably a component or a part of the page: search the project, ask if unclear". Before the agent gets the job, its own server fills in what the page couldn't (`withComponentFiles()` in [locate.ts](../packages/cli/src/locate.ts)): a project component's file relative to the agent's folder (the list's are relative to the workspace's root), and a component or unlisted name with no file, by its declaration, across the workspace. With a `/` action, they go in the task with its note. An answer to the agent's question is words only, for now.
- **In the thread**, a sent message's mentions show apart from its words (placeholder look, pending the design).

### Props

`/props`, offered when the selection is one component's instance (its top-level element, as the hover label names it), lets the designer change it through its props, from a list, instead of describing it ("make it the dark one").

- **Pilot reads the instance's props itself**, from the framework in development (`componentProps()` in [dom/component.ts](../packages/overlay/src/dom/component.ts)): React's fiber (`memoizedProps`, from the copy on screen: the one a DOM node points at can be the one from before the last render), Vue's instance (`props`). Strings, numbers and on-off values only; not handlers, children, class names or styles. Also where the instance is written (its parent's file). Not for Server Components: their props stay on the server.
- **What it can be set to lives in the code** (a union type, a cva or tailwind-variants config, a Vue `validator`), so a job asks the agent (`formatProps()` in [format.ts](../packages/protocol/src/format.ts)): read the component, change nothing, and return the props that change how it looks in its reply's `pilot` block (`props`) (`PropSpec`: options, on-off, text or number, the values it accepts, the default). Any model can do it: it's a basic job. The hub keeps them on the job (`propsOf()` checks them), and the page shows them as the agent's reply.
- **In the thread, a row per prop** ([PropsList](../packages/overlay/src/ui/components/PropsList/PropsList.tsx)), built from the property dialog's pieces: a select for options and on-off props, a field for text and numbers, each showing the instance's value on the page (else the default). The reply is split in two: its words in the green bubble, square at the bottom, and the rows in a box under it, on the darkest background, so the fields look as they do in the dialog (the owner's design). A long name is cut with an ellipsis; the whole name shows in a tooltip, with the agent's description of the prop as its second line when it gave one.
- **A pick writes a line in the comment being written**, never anything more: nothing changes on the page and nothing goes to the agent until Send (props are code, not a preview). The line is `name: value` (`tone: dark`), one per prop, replaced when it's picked again and taken out when the page's value is picked again ([propLines.ts](../packages/overlay/src/ui/components/CommentWidget/propLines.ts)); the designer can edit it, or type one by hand. Words, not chips: the comment reads as the designer wrote it, and the agent, who listed the props, reads it as such. Sent, Pilot still reads back the lines that name a listed prop with a value it takes (`propsInText()`), so the job carries them exact (`props` on the message: the component, where it's written, from → to) and Pilot checks them: the agent sets them where the instance is written, not in the component, and asks first when that line renders several instances (a loop over data) or the value comes from data. A row keeps showing a sent pick until the page has it. Not with a `/` action.
- **No preview:** a prop isn't CSS, so the page changes once the agent edited the code and hot reload ran (a few seconds). Rejected: re-rendering the instance with the new props from the overlay (it would reach into the framework's internals, and what shows wouldn't be the code).
- **Checked like an edit:** once the agent is done, Pilot reads the instance's props again, every 400ms for up to 6s (hot reload takes longer in some frameworks), compared as text. What isn't what the designer picked goes back once as a follow-up (`taskFollowUp()` in [prompt.ts](../packages/cli/src/prompt.ts)); after it, Pilot takes what the code gives.
- **Answered, the rows go:** once the designer wrote after a list, it shows only the agent's words: a pick there would start another round unseen. `/props` again for a new list.
- **Remembered, never stale:** each component's list is kept for the tab (by name and file). The next `/props` on it shows it at once, while the agent reads the code again; its reply updates that same message, so new props show and gone ones go, and picks already written stay (they're lines in the comment). Shown early, it isn't a reply to read: the thread counts it once the agent's in.
- **Not yet:** for one instance at a time.

### Tasks: Break and fix

`/break` asks the agent to stress-test the element with odd but realistic content (text far longer or shorter than the placeholder, long words like URLs, missing optional parts, many items, images in odd shapes or failing to load) and fix what breaks without changing its usual look: truncation or line clamps where text is cut, `min-width: 0` and `flex-shrink: 0` where flex squeezes the wrong items, wrapping, `object-fit` / `background-size` with a fixed frame ratio and a fallback for images. A distorted image keeps its box, so Pilot's check can't see it: the prompt has the agent read the code for it. The agent works out from the code where odd content would break it (trying content temporarily if it helps), fixes, and puts the real content back. Pilot checks it after like Make responsive, with the usual content: the designer-width comparison watches layout and type, not overflow or `min-width`, so fixes pass as long as the usual look holds, and test content left in the code shows up as a change there.

### The agent asks

When part of a job needs the designer's decision, the agent asks instead of guessing, and doesn't wait for the answer. The case it's made for is **shared code changed in only some copies**: the designer restyled one card, the cards come from one component, and the edit is for every card or a variation of this one.

- **Pilot says how many look-alikes each element has**: the elements like it on the page that the job leaves out (`lookAlikes` on the target, from the same search as Select similar, [page.md](page.md)), and, in a React or Vue app, which component they're instances of (`lookAlikesOf`, with the element's component and file in `source`: [page.md](page.md), *Components*). The prompt gives the count; the agent tells from the code whether they share it. Every job's guidelines say when to ask (`SHARED_CODE` in [format.ts](../packages/protocol/src/format.ts)): only when they share it and not every copy is in the job.
- **The agent does the rest of the job, leaves that part, and asks** in its reply's `pilot` block (`question`: one short sentence and up to four one-click `choices`). Its other jobs go on.
- **Three answers for shared code, with one meaning for every agent** (`SHARED_CHOICES` in [format.ts](../packages/protocol/src/format.ts)), the agent's suggestion first: **All of them** changes the component itself; **Only this** changes it where this instance is used, with what the component already accepts (classes through its `className`, merged the project's way, or one of its props), else the smallest pass-through, never a variant or inline styles; **New variant** adds a named option the way the component defines variants (`cva`, a `variant` prop) and uses it here. Why three: in component code "only this one" is two different things, a one-off at the call site or a reusable option, and only the designer knows which they mean, while the agent knows what the code allows. The labels are short so the three fit on one line. The answered job spells out what the chosen one asks (`sharedChoiceMeaning()`), so it doesn't depend on the agent remembering the guidelines.
- **No question when the answer is known:** the designer said it (in the comment or note: "only here", "every card", "as a variant"), every copy is in the job, or nothing else uses that code.
- **Pilot asks it in a comment thread** on the job's first element: the job's own thread (a comment's), else the element's thread, else a new one about all of the job's elements (`PilotSession.ask()`). The choices are buttons under the question, the first (the agent's suggestion: it lists it first) the more prominent; the designer can also write an answer. The thread needs them (see below), and the job shows no loader meanwhile: the question says where it stands.
- **The job is held, not checked:** it stays on its elements (their changes wait, its previews stay), since what the agent left isn't in the code yet.
- **The answer** (a choice, or the designer's next message in that thread) sends the job back to the agent, preferably the one that asked (`POST /jobs/:id/answer`, `Hub.answer()`), with the question and the answer (`answered()` in [prompt.ts](../packages/cli/src/prompt.ts)), resuming the session that asked. When it's done again, Pilot checks it like any job, and the agent's notes are its reply in the thread. A job asks once: a second question is dropped, and the agent says what's still open in its notes.
- **Why not block:** waiting for the answer would hold up the agent's other jobs, and the designer may answer much later. Why not apply first and ask after: undoing a variation to change the component (or the other way) is more work than asking first.

### Threads that need you

A thread needs you when the agent spoke last. Replying sends it back to the agent, resolving removes it, opening it changes nothing (`PilotSession.attention`, `needsYou()`).

- **Every unresolved thread shows on its element**, with either tool: its outline, and a **comment icon** on its top-right corner that opens the thread (switching to Comment). While its latest comment is with the agent, the loader shows instead. No numbered pins: the icons mark the threads. It stays at the far right of the corner; the selection's actions and a job's loader sit on its left.
- **The Comment button** gets a pill with how many need you ("2 comments to review"). While Comment is on, each click opens the next one, oldest first, wrapping around, scrolled into view and flashed (threads on other pages skipped). Esc closes the widget and drops the selection; the next Esc turns the tool off.

## Closing

Close, the toolbar's last button, closes Pilot on the whole site: `POST /quit` (the page's own origin only), and the hub sends the site's pages a `quit` event (its other tabs close). Nothing else: jobs go on (Pilot keeps running the agent for them, and checks them when it's open again), and the shortcut opens it again. Since agent runs there's no chat to release: until then Quit also ended the agents' waits, so their chats stopped the loop. Details in [page.md](page.md), *Launching and quitting*.

## When something's stuck

Pilot never leaves a loader spinning with no clue why. A job nothing will move by itself is **stuck**, and the page says what's wrong and what to do (`PilotSession.stuck`, [session.ts](../packages/overlay/src/bridge/session.ts)):

- **A run failed** (`agent-error`): Pilot couldn't run the agent for a job (not installed, not signed in, the run failed). Said at once, with the run's own title and what to do (*Agent runs*, *Errors*), until the designer sends again or cancels the job.
- **Pilot isn't running for this site** (`offline`, `no-agent`): the page can't reach the hub, or reaches it but nothing runs for its site: "Run npx usepilot in your project's folder".
- **An older Pilot is running** (`older-agent`): the page can't reach its hub, but an older version's answers on its port (4747 + an older bridge version, newest first; `olderHub()` in [client.ts](../packages/overlay/src/bridge/client.ts), at most every 10s, only on the default address): an agent's chat on the MCP loop, or an older `npx usepilot`, which can't reach this page. Said with jobs or without, on Comment and Send both, as "Pilot isn't running for this site" with the same command. The page can't read the answer (no-cors), only that something's there: another app on one of those ports would say it too, a rare case taken for the clue it gives.

Each is said only once it has lasted (past a reconnect; a failed run at once), and goes by itself when it's solved. Until agent runs, "isn't listening" said when no chat had asked for a job for a while: there's no chat to listen now. Not stuck: a job queued behind one an agent is on, a question waiting for the designer's answer, a job being checked. An agent that leaves mid-job (its chat closed) isn't a stuck state either: the hub puts its jobs back in the queue (`Hub.unregister`), for another chat or the same one back. A long task isn't called stuck (Pilot can't tell slow from stuck): its tooltip says how long the agent has been on it ("· 12 min").

Where it shows, the owner's design: the toolbar's pill turns red with "!", its tooltip the message on two lines: on Comment and Send both when an older Pilot is running (whatever goes next can't reach Pilot), else on the button the stuck jobs belong to (Comment for comments and tasks asked in a thread, Send for the rest); the elements' corner loader gives way to a red warning (still), its tooltip the same, and hovering still turns it into an X that cancels the job; the element's fill stops breathing, and the jobs button goes when every job is stuck (none is being worked on); in the thread, the reply to come becomes a red reply. A send that fails (an attachment that didn't upload) is a red reply too, and the draft stays.

## Elements being worked on

A job that isn't finished (waiting, an agent on it, being checked, its follow-up) is **on elements**: a task's or a comment's element, the elements an edits job changes (`PilotSession.jobOn()`, `busy`; found again by selector after a reload).

- **It shows**, selected or not, while Pilot runs: the element keeps its outline, its fill breathes (opacity only, so it runs on the compositor; still with reduced motion), and a **loader** takes its top-right corner ([SelectionActions](../packages/overlay/src/ui/components/SelectionActions/SelectionActions.tsx) `busy`), a stepped rotation so the graphics card turns it alone. Its tooltip says what the job is about, then where it stands: the comment's own words (“Make the price bigger”, with the edits that went with it), the task (Make responsive, Props of ProductCard), or the edits by what they are ("3 style changes", "1 text change": changes are always said with their kind, `changesLabel()`). On the page, a thread whose job is with the agent shows only the loader: the comment icon means a reply to read, and showing it all the time would lose that. Selected, its icon sits beside the loader, the selection's own action, to open the thread and see the whole conversation. The loader is always the far-right icon, with its tooltip hanging left (clear of the panel beside the element); its × on hover is Nucleo's xmark. Placeholder look, pending design.
- **Cancel is on the loader:** hovering it turns it into an X while the agent isn't done, and a click takes the job back ("Cancel job"; a job on several elements is cancelled whole).
- **No second job goes to it.** Send leaves its changes out: they **wait**, and go as a job of their own once the job on it is finished (`held` in [session.ts](../packages/overlay/src/bridge/session.ts), saved by selector). So two agents, or the agent's edit and the designer's next one, never cross on one element. Only the changes of the elements that waited go then, not edits made meanwhile elsewhere. Send's tooltip says "Queued" (or "Sent; some queued"), and Send stays dimmed while all that's unsent waits. A cancelled job doesn't release what waited for it: its own changes are unsent again, and everything goes with the next Send.
- **Comments wait too.** One written while a job is on the element shows in the thread at once, says "Queued", and goes once the job is finished, with any others that waited, as one job carrying the whole thread (`waiting` on the message). The agent couldn't read it mid-job anyway (a run reads its prompt once), and this way a second run can't take it and edit the same code meanwhile, nor can its change land while Pilot is still checking the job before (which would send a follow-up undoing it). A comment's own job counts too: the next comment on that element waits for the agent's reply. Unlike held changes, waiting comments also go when the job is cancelled.

**The job list** ([JobList](../packages/overlay/src/ui/components/JobList/JobList.tsx)) isn't shown for now: what a history of the session should hold is open (what changed, before → after; how it landed; the files touched; a summary to copy). Its `statusText` and `whatText` give the loaders' tooltips.

## The hub

[packages/cli](../packages/cli): [hub.ts](../packages/cli/src/hub.ts), [server.ts](../packages/cli/src/server.ts), [agent.ts](../packages/cli/src/agent.ts), [run.ts](../packages/cli/src/run.ts).

- **One per machine and bridge version**, on `127.0.0.1:` 4747 + `BRIDGE_VERSION` (4754 for version 7, agent runs; `PILOT_PORT` overrides it). Projects on the same version share it; a project on another version runs its own, so two versions never block each other on one port (before 0.7.0, every version used 4747). It lives in the first `npx usepilot` (or `usepilot mcp`) process; later ones get `EADDRINUSE`, check `/health`, and talk to it over HTTP (`/agents/*`). When the hub's process ends (its chat closed), the next call of another agent fails to connect and that process takes over the port.
- **State is in memory only.** The page posts its unfinished jobs again on every connect, and the hub must accept a job posted again (idempotent by id), so a takeover loses nothing.
- Remote agents ping regularly and are dropped after missing a few.
- **Versions:** every process checks the hub's bridge version (`/health`, `BRIDGE_VERSION` in `@pilot/protocol`) and refuses to join one of another version (7 since agent runs: a job's `session` and `error`, `/agents/job`, quit closing pages only). With a port per version, that only happens when `PILOT_PORT` puts two versions on one port; the message says so.
- **Follow-ups:** `POST /jobs/:id/retry` puts a done job back in the queue once (`attempt: 2`, with its `differences`), given first to the agent that did it if it's waiting (`Hub.retry()`).
- **Routing:** jobs are filed by page origin (`localhost`, `127.0.0.1` and `[::1]` count as the same, `originKey()`): an agent only gets jobs from the page it launched for. Two repos open at once stay separate. The runner takes up to three jobs at once, so the designer can run tasks in parallel (`dispatch()` in [hub.ts](../packages/cli/src/hub.ts) gives each to a free slot), and an element with a job on it holds the next one, so two runs never edit it at once.
- **Security:** the page's origin comes from the `Origin` header, never from the request body; jobs are only accepted from an origin Pilot runs for (`npx usepilot` registers it), so another website can't hand prompts to the agent. Agent routes refuse any request with an `Origin` (browsers send one, Node doesn't). Keep both checks for every new route.
- **The project's folder** (`AgentInfo.folder`, the runner's project folder) goes to the hub with the agent, for `POST /components`: the hub keeps it to itself, and what it sends pages (the agents, `launch`, jobs) never has it.

## The page side

### Finding elements again

Threads, jobs and the edit history are saved per tab and find their elements again after a reload (`findTarget()` in [dom/target.ts](../packages/overlay/src/dom/target.ts)). The selector Pilot saved has the element's classes, and those change: a prop sets a variant (`card--light` → `card--dark`), the agent edits a class. So:

1. **Its selector**, when the element it finds has the saved text (two cards that swapped classes would otherwise trade threads).
2. **Else where it is**, by tags and positions only (`at`: `#react > main > div > article:nth-of-type(1)`, from the nearest id), with its text or its component (a prop may have changed the text too).
3. **Else its path without classes**, for what was saved before `at`: the one element there with its text and component.
4. **Else its selector's element** (its text was changed on purpose), or none: a wrong element would be worse than none.

A thread found another way saves its element's selector as it is now, so the next look is direct.
