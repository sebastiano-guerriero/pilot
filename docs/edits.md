# Edits: recorded, shown, handed off

How a change goes from an editor to the agent. Pilot never edits source files and never touches the elements' own `style`: it records plain-CSS intent, shows it through a stylesheet of its own, and hands it to the agent as a change set.

## The history

[edits/history.ts](../packages/overlay/src/edits/history.ts). **Every property change must be undoable**, so every one goes through `EditHistory`: editors call `onChange(property, value, { gesture })` and never write styles themselves. The history:

- records the change (element, property, value, widths, states, removal) and rebuilds the **preview** from every change in effect. Nothing is restored on undo: the undone change is just left out;
- lets a change replace Pilot's earlier ones it covers for the same element, widths and states: the same property, or a longhand of it (`padding` replaces `padding-top`, `grid-column` replaces `grid-column-start`). A change to `""` drops Pilot's value;
- groups a continuous interaction into one undo step: every change with the same `gesture` object is one step, so a drag passes the same token on each move;
- skips no-op changes (setting what Pilot already sets for those widths, or `""` where it sets nothing);
- can `revert()` one property of the ongoing gesture (dropping the step if nothing is left), behind the editors' `onRevert`;
- answers what Pilot sets at a width (`valueOf()`, a longhand read out of a shorthand) and whether a property is removed there (`removalOf()`), for the fields, and lists the changes in effect (`changes()`: one per element, property, range and states) for the change set.

**Cmd/Ctrl+Z** undoes and **Cmd/Ctrl+Shift+Z** / **Ctrl+Y** redoes, handled in `App`, across selections, unless there's nothing to undo or redo or the user is typing in one of the page's own fields (or a comment, where they undo the text).

The history belongs to `mountPilot` (one per page load), not the UI, so quitting and relaunching keeps it.

## The preview

[dom/preview.ts](../packages/overlay/src/dom/preview.ts). Each edited element gets a `data-pilot-edit` id, and each change in effect becomes a rule in a `<style data-pilot-preview>` that Pilot puts first in the document's head (or the element's shadow root), in the order the changes were made:

```css
@layer pilot-preview {
  [data-pilot-edit="1"] { padding-top: 4px !important; }
  @media (min-width: 960px) { [data-pilot-edit="1"] { padding-top: 30px !important; } }
}
```

- **A base change sits beside the page's own CSS** ([dom/anchored.ts](../packages/overlay/src/dom/anchored.ts)): a change with no widths and no states is the element's base value (see *Widths*), so it isn't in the layer: Pilot puts it in the page's own stylesheet, right after the declaration it replaces, for this element only, nested in that rule: `.pt-4 { padding-top: 1rem; &:where([data-pilot-edit="1"]) { padding-top: 20px; } }` (right after the rule, `:is(.pt-4):where(…)`, where a rule can't hold nested ones). The browser's cascade then does what the code will: the project's breakpoint (`md:pt-3`), state (`:hover`) and condition (`[data-checked] > *`) rules still win where they apply, since they came after the base or are more specific. In the browser's copy of the stylesheet only (CSSOM), never the files. A hot reload replaces a stylesheet (Pilot's rule goes with it) and a component restyled with other props gets another class (CSS-in-JS): while any base change is shown, Pilot watches the head's stylesheets and those elements' classes, and puts each back beside the base declaration found again (`renderAnchored(…, check)`), once a frame at most. A property the element declares nowhere, or only in its style attribute, has nothing to sit beside: it goes in the layer, as before. Tried first on the sandbox (Tailwind v4) and plain CSS, 2026-11-26, the owner's call: an `!important` base change overrode the project's breakpoints everywhere, and the prompt then told the agent to flatten them.
- **Changes for widths and states too** (the owner's call, 2026-11-26: in the layer, a "from 768px" change beat the project's 1200px rule too, and a hover change its focus styles): beside the project's own rule for the same widths and states when it has one (its `md:pt-3`, inside its `@media`; its `:hover` rule, nested: `.btn:hover { …; &:where([data-pilot-edit="3"]) { … } }`), else a rule of their own placed where the project's would go: a "from" width after the project's smaller "from" breakpoints for that property and before its larger ones, a "to" width after its larger "to" ones, a range after every rule overlapping it, a state right after the element's base rule (`:is(.btn):where(…):hover`), so its other states, later, still win when they apply. The project's media queries are read as ranges (`mediaRange()` in [dom/breakpoints.ts](../packages/overlay/src/dom/breakpoints.ts): `(min-width: …)`, `(width >= 48rem)`, `(768px <= width < 1024px)`; anything else, orientation or color scheme, isn't a range and isn't placed among them), and every declaration of the property, whatever the width, comes from `declarationsOf()` in [dom/declared.ts](../packages/overlay/src/dom/declared.ts); where several rules are the project's own for the same widths, the cascade's winner (`beats()`).
- **An `!important` in the project is matched** (the owner's call, 2026-11-27: with Tailwind's `!pt-4` or `padding: 1rem !important`, the field showed the new value and the page didn't change, and someone who didn't write the code can't tell why): when a declaration of the project's that applies where the change does (those widths, those states or none) is `!important`, Pilot's is too, in the same spot, so it wins as the edited code will. The change set marks it (`important` on the change) and the prompt tells the agent to change that declaration and keep it important (its guideline: no new `!important`, keep the project's). Nothing is said to the designer: it just works. The one thing nothing beats is the element's own `style` attribute with `!important`: while that property's editor has the focus, the dialog's footer says the page won't show changes and the agent still makes them.
- **Widths:** a change for some widths sits in `@media` with `min-width`/`max-width`, both ends included, so resizing shows each range's changes in their range and the page's CSS elsewhere. Among Pilot's rules the later wins. This is why the preview is a stylesheet and not inline styles: resizing shows the truth.
- **The layer wins over the page's CSS** (changes the element declares nowhere, with nothing to sit among, and removals that can't skip the project's rule: see *Removing a value*): every declaration is `!important`, in a layer declared before any of the page's (the sheet comes first), and important declarations in the first layer beat every other stylesheet's, layered (Tailwind v4's `!p-4`) or not. The one thing it can't beat is the app's own `style` attribute with `!important`.
- **States** go in rules for those states, and only apply in them: the element isn't shown in its states while their pills are set (it was, before: forcing them over the page hid how its other states behave). Hide Pilot (Option+P) and hover or focus it ([property-dialog.md](property-dialog.md), *States*).
- **Values** are written by the browser (a scratch style declaration), so one it doesn't accept is left out.
- An element loses its `data-pilot-edit` when it has no rules left, and the sheet is emptied when there are none.
- **A value change is written in place:** when only values change (the same rules in the same order: each frame of a drag, a field stepped), they go into the sheet's rules through the CSSOM (`updateValues()`), and the browser restyles only the elements those rules select. Rewriting the sheet's text made it reparse it and restyle the whole page (a new sheet with a cascade layer): ~10ms a change on a 600-element page against ~0.3ms, so a color picker's drag went past its frame. Any other change (a rule added, removed, moved) rewrites the text. The text then lags behind the rules: `previewCss()` reads what's shown, as written (tests; happy-dom doesn't parse `@layer` blocks, so there it's always rewritten). A style rule has `cssRules` too in browsers with CSS nesting (empty), so `@media` is told by having no `style`.
- Tests can give `EditHistory` another `Preview` ([test/inlinePreview.ts](../packages/overlay/src/test/inlinePreview.ts) writes inline styles, ignoring widths) to read what an edit did from `element.style`.

## Declared values

[dom/declared.ts](../packages/overlay/src/dom/declared.ts). What fields show: for each of an editor's properties, Pilot's own value at the window's width (`EditHistory.valueOf()`), else the winning declaration of the page's own CSS: its stylesheets, Tailwind classes and the app's inline styles (`fieldValues()` in the dialog), as written (`50%`, `var(--space-4)`), or nothing when nothing declares it. Pilot's preview sheet is left out of the walk (`isPreviewSheet()`): its edits come from the history, which knows them exactly.

- **Matching rules.** It walks the stylesheets of the element's root (the document or a shadow root, adopted sheets included) in document order, following `@import`, and keeps style rules whose selector matches the element and whose conditions hold: `@media` via `matchMedia`, `@supports` via `CSS.supports`, `@scope`'s start. Nested rules are resolved (`&`, descendants of the parent selector).
- **The cascade.** `!important` beats normal; then inline styles beat rules; then `@layer` order (later layers and unlayered styles win normal declarations, the order flips for important ones, styles directly in a layer beat its sub-layers); then specificity (`:is`/`:not`/`:has` take their most specific argument, `:where` counts nothing); then order of appearance.
- **Shorthands and logical properties.** A side also comes from its logical longhand (`padding-inline-start`), the logical pair (`padding-inline`, which Tailwind's `px-4` writes) and the shorthand (`padding: 10px 18px`), assuming horizontal, left-to-right text. CSSOM can't expand a shorthand containing `var()`, so its text is split by hand: `calc(var(--spacing) * 4)` applies to every side.
- **Cost.** One walk is shared by all the editors in a render, cached, and refreshed when the stylesheets or the element's classes change. About 3ms per thousand rules.
- **Known gaps.** `@container` conditions can't be evaluated from script, so those rules are skipped. `@scope`'s end bound is ignored. Cross-origin stylesheets can't be read. The browser's own styles aren't visible, so a `<ul>`'s default padding counts as nothing declared. The app's `style` attribute with `!important` wins over the preview.

## Removing a value

[edits/clear.ts](../packages/overlay/src/edits/clear.ts). Clearing a field means "this element doesn't set this property", never `0`, `none` or the default. Editors pass `""`, and the dialog's `clearProperty()` decides:

- **When only Pilot set the value**, clearing just drops Pilot's edit: there's nothing to remove.
- **When the page's CSS sets it** (a stylesheet rule, a Tailwind class, the app's own `style` attribute), Pilot records a **removal**: `{ property, from, to: "", removed: true, source }`, where `source` (`StyleSource`) says where the page declares it: the `style` attribute, or a rule's selector with how many elements on the page it matches. `formatPrompt()` marks the row *removed* and tells the agent to stop declaring it for this element, and for a rule other elements share, to remove it for this element only unless the designer's note says otherwise.
- **When only a reset sets it** (a rule for every element, `*`: Tailwind's preflight `border: 0 solid`, `margin: 0`; or naming only an element and setting nothing of its own, `button { color: inherit }`), the element doesn't set it either, so it's the first case: Pilot's edit is dropped, no removal (`isFromReset()`). A removal there would ask the agent to change the reset for every element to clear one field. Found with the border editor (2026-11-24): moving a border to one side clears the all-sides properties, which the reset declares on every element.
- **The field is empty**, the Pilot way of saying no value is set.
- **The page previews it exactly, for that field's pills** ([dom/excluded.ts](../packages/overlay/src/dom/excluded.ts), the owner's call, 2026-11-26: an empty field only means "don't declare it here", and whatever another pill declares must still apply): the project's rule for exactly those pills (the base, a breakpoint, a state: what the field read) stops applying to this element, with a skip clause on each of its selectors (`.btn:hover:not([data-pilot-skip~="r2"])`, the same specificity; the element carries the token), and a copy of it for this element only, without the cleared properties, sits right after it (`:is(.btn:hover):where([data-pilot-edit="5"]) { … }`). The cascade then shows what the code will at every width and in every state: hovered at 1300px with a hover background cleared, the project's own value for that width, not a fixed fallback. Other elements the rule matches are untouched, the rule's selector is put back when no element skips it, and reading the page's CSS leaves the skip clause out (the field and the change set still see the project's rule). Pilot's own changes for that element beside the skipped rule move into the copy. Where it can't (the property in the element's `style` attribute, a rule for a pseudo-element, or a DOM that can't change a rule's selector), the old preview, in Pilot's layer: the next declaration in the cascade (`declaredWithout()` leaves the removed rule out), or `revert` when no other rule declares it.
- **Its fallback**, in that case and for the rules named with it: the next declaration in the cascade (`declaredWithout()` leaves the removed rule out), or `revert` when no other rule declares it. A rule declaring the very same value is the same declaration repeated, so it's left out too, and named in the removal (`source.also`) for the agent to remove from as well: Tailwind composes `box-shadow` from several classes (`shadow-card`, `ring-1`), each declaring `var(--tw-inset-shadow), …, var(--tw-shadow)`, and removing every shadow of a card brought them all back. A rule with another value is a real fallback, and shows (`.card`'s `16px` under `.card--big`'s `24px`). `revert` falls back to the browser's own styles (a list's padding, a heading's margins), which Pilot can't read, and otherwise to the inherited value or the default; `unset` would skip the browser's styles and show a wrong preview. The fallback is only for the preview: the agent gets "don't declare it here" and the removed value (to find the declaration), never the fallback, which the cascade gives anyway. For a value from the `style` attribute, the preview is the stylesheets' value.
- The page's own value is the declared one, and the preview sheet is left out of declared values: setting `20px` over a stylesheet's `16px` and then clearing removes the `16px`.
- With the width chip set, the removal is for those widths: the project's rule for exactly that breakpoint.
- It's undoable like any change, and typing a value afterwards replaces it.

Once the agent applies it, the page's CSS no longer sets the property, and the field is empty for the same reason it is now.

## Widths

A change for some widths carries `widths: { min?, max? }` (`WidthRange`: CSS px, both ends included); without (and without states) it's the element's **base value**: the one it declares without a media query or a state (`baseValue()` in [dom/declared.ts](../packages/overlay/src/dom/declared.ts)), and the project's breakpoint, state and condition rules keep winning where they apply. Pilot builds on what's there (the owner's call, 2026-11-26). Before, it meant "every width": shown over the project's breakpoints, and the agent was told no media query should override it, so `pt-4 md:pt-3` came back flattened. Which widths a change is for is decided once, as it's made (`applyChange()` in [edits/reach.ts](../packages/overlay/src/edits/reach.ts)): with no width chip, the widths of the rule that applies at the window's width (`md:pt-4` between md and lg: `from 768px`), so the change is that rule's, as if the chip had said so; with a range, Base or All widths, the chip's ([property-dialog.md](property-dialog.md), *Viewport widths*). A recorded change keeps its widths after a resize. Editors don't handle widths: the dialog routes every editor's changes through `applyChange()`.

`formatPrompt()` gives every change a Widths column (`from 1200px`, `to 767px`, `768–1199px`, `1108px only`, worded by `describeWidths()`, which the chip uses too, or `base`). It tells the agent to use the project's breakpoints when one matches (or is within a few pixels), else a custom media query, and that "base" is the base value: change it where it's declared without a media query or state, and keep the project's media queries, states and conditions as they are. A base change's From and source are the base declaration's (`pt-4`'s line), not what wins at the window's width; a change for widths, the project's rule for exactly that breakpoint (`rangeValue()`), or none (a new breakpoint: From "not set"). When the old value comes from a rule inside `@media`, `StyleSource.media` holds the condition (`mediaOf()`), and the prompt says where it sits today. The fields show the same: the value where a change would go ([property-dialog.md](property-dialog.md), *Viewport widths*). Pilot shows breakpoints as widths; the agent names them.

## States

Changes record the state pills' `states` the same way, through `history.apply(…, { widths, states })` / `clearProperty(…, widths, states)`; fields read values for exactly those states. Editors don't handle states either. The color scheme (`dark`, `light`) and pseudo-elements (`before`, `after`, `placeholder`) are states too ([property-dialog.md](property-dialog.md), *States*): in the preview, a pseudo-element goes last in the selector (`:hover::before`, `stateSelector()`), and a scheme around the rule the project's way, a class after the subject or a media condition (`schemeParts()` in [dom/scheme.ts](../packages/overlay/src/dom/scheme.ts)). The prompt adds a State column (only when a change has one) and tells the agent to use the project's form (`hover:`, `:hover`; the project's dark mode for `dark`, its `light:` or the same mechanism for `light`; `::before`, with a `content`). Pilot can't put an element in a real hover or focus to measure it, so a state change is accepted on the agent's word after done (`unchecked`).

## Conditions

A condition described in words (Create modifier, [property-dialog.md](property-dialog.md), *Conditions*) is a third modifier beside widths and states: changes record it (`history.apply(…, { condition })`, `Entry.condition`: the designer's words and Pilot's CSS reading, plain JSON, saved with the history), and every identity check takes it (`sameCondition()` in [edits/condition.ts](../packages/overlay/src/edits/condition.ts), by its CSS: two phrasings of one condition are one). A change under a condition is never one of the element's own values (the fields without it, the reach's candidates, the `/` menu's used rows leave it out). It always goes to Pilot's own rule for the condition, for the width chip's widths or the base (`applyChange()`); the page's own conditional rules (`.card:focus-within .title`) aren't read yet, so a field under a condition shows Pilot's value or nothing, and a cleared field just takes Pilot's value off.

In the preview, condition changes stay in Pilot's layer, never beside the page's rule (there, without the condition, they'd apply all the time): the condition's selector with the element in `&`'s place, the states after it (`.card:focus-within [data-pilot-edit="3"]:hover`), its media with the widths' (a media type first: `print and (min-width: 768px)`). **As if true / as if false** (`history.simulate()`) is the preview's only, never saved or sent: true leaves the condition out of its changes (they show as for the element as it is), false leaves them out. The page is never touched to make a condition hold.

The change set carries it (`StyleChange.condition`; its From is "not set", the page's rule for it not being read), and the prompt adds a When column with the designer's words and a note with Pilot's reading: the agent writes it the project's way (Tailwind's `group-*`, `peer-*`, `has-*`, `data-*` or an arbitrary variant; CSS nesting), following the words where they disagree. After done, a condition change is checked only while the condition holds on the page as it is (not simulated), else accepted on the agent's word (`unchecked`).

## Text changes

[dom/text.ts](../packages/overlay/src/dom/text.ts). Text edited inline ([page.md](page.md)) is the one non-CSS change.

- What's edited is a **text run**: the text between an element's child elements, its text nodes in a row (a comment between them, like React's `<!-- -->`, doesn't break it). A text-only element has one run, its whole text.
- Each run is recorded in the history like a CSS change, under a reserved property (`textProperty(run)`: `text` for run 0, `text:1`, `text:2`…), with no widths or states: undo, reloads, Send, jobs and the check after done work the same, each run on its own.
- The change set gives them as the edit's `texts: [{ from, to }]` (whitespace runs as one space, trimmed), apart from the CSS changes; `from` is the page's own text, or the one it had when changed while the element isn't on the page. The prompt lists them under *Text (from → to)* and tells the agent to change the copy where it comes from (the markup, a prop, a translation file) for this element only.
- **The text preview** is the only place that writes an element's text. CSS can't replace text, so it writes into the run's own text nodes (the first gets the text, the others are emptied), **never replacing or removing them**: a framework that holds them still finds them, and the runs keep their places. A MutationObserver on those elements takes what the page writes into them (a re-render, hot reload after the agent's edit) as its own text and shows Pilot's over it again.
- That's what the check compares: a text change landed when the page's own text in that run is the designer's (whitespace aside).
- Descriptions (`describeElement()`'s snippet, an ancestor's too) use the page's own text, so the agent greps for what's in the source.
- **Known limits:** a run is found by its place among the element's runs, so a re-render that adds or removes child elements before it can shift it. A server-rendered page hydrating after Pilot restores a text change may log a hydration mismatch; the framework re-renders and the observer takes the new nodes in.

## The change set

`ChangeSet` in [protocol/src/types.ts](../packages/protocol/src/types.ts): page URL, viewport, an optional designer note, and per element its target and `{ property, from, to }` changes (with widths, states, removals), plus `texts`. `buildChangeSet()` ([edits/changeSet.ts](../packages/overlay/src/edits/changeSet.ts)) builds it from the history: per element, the page's own `from`, `to`, removals, widths and states.

**The target** comes from `describeElement()` ([dom/target.ts](../packages/overlay/src/dom/target.ts)):

- a selector guaranteed to match only that element, preferring ids and adding `:nth-of-type()` only where siblings would be ambiguous;
- a readable path like `main > section.hero > h1` (classes help the agent find it);
- a trimmed text snippet the agent can grep for.

**The prompt.** `formatPrompt()` ([protocol/src/format.ts](../packages/protocol/src/format.ts)) turns it into a Markdown brief that tells the agent to map the values to the project's conventions (no inline styles), prefer existing tokens and utilities and report any value it had to approximate, and ask before changing a shared component everywhere. It's the prompt of the job Pilot runs the agent for ([handoff.md](handoff.md), *Agent runs*): a question or props go in the reply's `pilot` block, and Pilot checks the result after. (Copy prompt, which pasted the same text into any chat, is gone: it handed over edits only.)

## Edits survive reloads

[edits/persist.ts](../packages/overlay/src/edits/persist.ts). The history (changes, undo and redo) is saved in the tab's `sessionStorage` after every change and restored when Pilot mounts again: after a reload the preview comes back, undo still works, and unsent changes are still there to send. A new tab starts clean.

- Each change keeps how to find its element (its unique selector, taken at the first change) and the page it was made on. Anything new the history records must be plain data (JSON-safe) apart from the element, and found again from the change's `target` after a reload.
- On restore, an element found on this page gets its changes back. One that isn't (another page of the app, or not rendered yet) keeps its changes on a detached stand-in, still in the prompt, and finds its element again later (`reattach()`: on launch, on selecting an element, on `popstate`).
- **Known limit:** an element whose selector changed (a list reordered, classes renamed) can't be found again.

**Discard** (the toolbar's button after Send, the owner's call) takes the changes not sent yet off the page: `EditHistory.discard()`, one undo step. The changes already sent (a job on them) stay, and a sent value that an unsent change replaced is back in effect: the step is a Clear that keeps the sent changes, as the same entries, so a job's `settle()` and `unsend()` still reach them (saved with the step, so through reloads too). What was waiting to go after a job on its element (held, see [handoff.md](handoff.md)) doesn't anymore: brought back by undo, it waits for the next Send (`PilotSession.discard()`). Rejected: discarding everything (`EditHistory.clear()`, still there, no button), which would take the previews of the changes an agent is applying off the page while it works. There's no confirmation: undo brings them back.
