# Pilot: notes for agents working on this repo

Read [docs/README.md](docs/README.md) first: the map of the docs and how to write them. Then read the doc for the area you're changing ([docs/product.md](docs/product.md) for what Pilot is). The root [README.md](README.md) is for people who want to use Pilot: what it is and how to install it. Keep it short, and don't put implementation details there.

## Keep the docs current

The docs in `docs/` are the project's living spec, and the memory between sessions. Update the doc for the area in the same change whenever you:
- add or change a behavior, or make a design decision (write down why, and alternatives that were rejected),
- add, remove or rename a package, script or command ([docs/development.md](docs/development.md)),
- ship a roadmap item (tick it, one line) or add new planned work ([docs/roadmap.md](docs/roadmap.md)),
- resolve an open question (move the answer into the area's doc),
- change how Pilot is installed or set up: the root [README.md](README.md) and [packages/usepilot/README.md](packages/usepilot/README.md) (npm's page), both.

Write behavior and reasons, not what the code already holds (sizes, colors, timings, lists kept in one file). Fix what's stale when you see it. `pnpm test` checks the docs' links.

## Product rules

- **Pilot is for every agent and every model; none is prioritized.** Whatever an agent needs to do a job well goes in the job's prompt, which every agent gets the same (`formatPrompt()` in `packages/protocol`, `jobPrompt()` in `packages/cli/src/prompt.ts`); what differs per agent is only how Pilot runs it (its flags and output, `AGENTS` in `packages/cli/src/agents.ts`). Advice for one vendor's model or product ("hand it to Opus") is said generically ("a more capable model, if you can"); facts about how an agent behaves (its sandbox, its flags) are fine. `format.test.ts` checks the prompts name no model.
- **Pilot runs the agent for each job** (`npx usepilot`, [docs/handoff.md](docs/handoff.md), *Agent runs*): the agent's command-line tool, the prompt on stdin, in the project's folder, with the permissions the designer gave that agent, as in its chat: what they allowed runs, the project's files can be edited, and what the chat would ask about is refused (no one is there to answer). Never a flag that skips permissions (`--dangerously-skip-permissions`, `--force`), nor Pilot's own limits on top. Keep that for every agent added, checked by `scripts/agent-runs-check.mjs` on macOS, Windows and Linux (the Agent runs workflow): **if it can't work on Windows, it's a dead end.** Nothing waits in an agent's chat.
- **Pilot never reaches production.** Nothing Pilot sets up may run on a server or be output by one, whatever a request says. `mountPilot` does nothing outside a development address (`isLocalHost()` in `packages/protocol`); `init`'s loading steps gate on the build's development flag, or, for a site without a bundler, on Pilot's own file being on disk and the project's development setting, never on request headers. Keep both; anything new that loads or runs Pilot gets the same guard.
- Pilot never edits source files. It records plain-CSS intent (`ChangeSet` in `packages/protocol`), and the agent translates that intent into the project's conventions. Text edited inline is the one non-CSS change: a history entry per text run (`textProperty(run)`: `text`, `text:1`…), the edit's `texts: [{ from, to }]` in the change set, shown only by the text preview (`dom/text.ts`), which writes into the run's own text nodes and never replaces or removes them. Don't write an element's text anywhere else.
- The overlay must stay framework-agnostic and isolated: Shadow DOM, no global CSS, and no dependency on the host app's packages. Preact is bundled into the overlay.
- Property editors are first-party and are designed by the project owner. Don't invent editor visuals without being asked. Build the plumbing and leave the look for review.
- **Every property change must be undoable.** Editors change styles only through `onChange(property, value, { gesture })`, which goes through `EditHistory` (`src/edits/history.ts`). It shows changes on the page through the preview stylesheet (`src/dom/preview.ts`). Never set `element.style`: Pilot never touches the elements' own styles. For continuous interactions (drags, scrubbing), pass the same `gesture` object for the whole interaction so Cmd/Ctrl+Z undoes it in one step. After an undo, inputs must show the restored value. To take back part of an ongoing gesture (e.g. Alt released mid-drag), use `onRevert(property, gesture)`. Never re-apply the old number: that leaves a fake edit.
- **Pilot never moves the page's elements.** Selecting them (and anything else short of an edit or a comment, which may move them on purpose) leaves the page exactly as it is. To bring an element into view, scroll the window only (`revealInWindow()` in `src/dom/reveal.ts`), never `scrollIntoView()`: it scrolls every container around it, `overflow: hidden` ones too, and the page's content shifts. Pilot's own lists scroll themselves (`scrollWithin()`). `reveal.test.ts` fails on any `.scrollIntoView(`.
- The property dialog never moves because of an edit: its spot is picked once per selection (and on window resize; with several selected, again beside each element added, `placeBy`), moves with the page's scroll, and only shifts to stay on screen (`dialogSpot`, `dialogPosition` in `PropertyDialog.tsx`; a shift up from growing taller sticks, `raisedSpot`, so shrinking keeps its top); the designer can drag it by the strip along its top edge. Don't re-anchor it to the element's live box.
- Editors show what they change on the page with `onInspect(areas)`. Whether an area hides the selection highlight (outline, dots, label) while its editor is in use is the project owner's call per property: padding, margin and gap keep it; border (no editor yet) hides it, since the outline sits on the border itself. Set this per area in `hidesSelection()` (`src/dom/boxModel.ts`), and ask the project owner when it's unclear. Editors of the Appearance group hide every highlight when they change a value (for a second; for a whole wheel drag), whatever they inspect (`clearsView()` in `src/editors/listOrder.ts`, per group).
- Build editors from the shared pieces: a one-value property is a `lengthEditor({ … })` (`src/editors/length/`), also for non-lengths: give the property a `kind` in `css/properties.ts` (integer, number, line-height, font-family, grid-line, grid-span, percent) and `name` for a row label that isn't the property name, a keyword property is a `keywordEditor({ … })` (`src/editors/keyword/`, a select, with icons per value if given), and a shorthand that splits into parts is a `splitEditor({ … })` (`src/editors/split/`: one value or each part, switched by a button in `PropertyRow`'s `action` slot; gap uses it directly; padding, margin and inset through `sidesEditor({ … })` in `src/editors/sides/`), a few values plus a custom field (aspect-ratio, flex-grow) is a `presetEditor({ … })` (`src/editors/preset/`), and a select that reveals other editors as rows (display, position) is a `revealEditor({ … })` (`src/editors/reveal/`, rows per value in `LIST_ORDER`), and a property too rich for one row (mask-image; filters, shadows) lists its values as chips in the row and edits each in a `PropertyPanel` beside the dialog (`src/ui/components/PropertyPanel/`). (Border is removed while its new component is designed; the old box diagram is gone.) Rows are a `PropertyRow` (label left, 128px value area right); value fields are `PropertyInputText` (a drag handle, `ScrubHandle`, is opt-in: pass `onScrub`, or `scrub: true` to `lengthEditor`; only where asked), and keyword pickers are `PropertySelect`. Don't fork these per property; extend their config instead.
- Every new editor that writes properties needs a place in `LIST_ORDER` (`src/editors/listOrder.ts`): the order of the empty-search list, and of the rows a revealing editor shows (display's grid and flex rows), kept by the project owner. Ask where it goes if it's unclear; `listOrder.test.ts` fails without it.
- Search terms: an editor is found by its label, the CSS property names it writes (and their logical equivalents, `padding-inline`), and Tailwind's class names (`aliases`, plus a row label that's neither, like `grid-columns`). Nothing else: no extra search keywords, no made-up shortcuts.
- Revealing properties: when a property or value brings others with it (`display: grid` shows grid-columns, gap, justify-content, align-items), the revealed ones are editors of their own, listed in the revealing editor's `embeds` and rendered as its rows. Only the revealing property reveals: searching a revealed one (`gap`) shows just that editor. Don't add revealed properties to the revealing editor's `properties` or `aliases`, or the search finds it too.
- Clearing a field means "this element doesn't set this property", never `0`/`none`/the default. Editors pass `""` to `onChange`, and the dialog's `clearProperty()` (`src/edits/clear.ts`) records a removal when the page's CSS sets it (the field stays empty, the page previews the cascade's fallback). Don't handle clearing per editor.
- Fields show declared values, never computed ones: read them with `declaredOf(props, property)` (`src/editors/declared.ts`), which comes from `dom/declared.ts` via the dialog. Pilot's own values come from the history (`valueOf`, `removalOf`), not the page. Don't read `element.style` or `getComputedStyle` for what a field shows. Computed `values` are only for steps and drags.
- Editors parse, display and step values with `src/css/values.ts` (`parseValue`, `displayValue`, `stepValue`), so every field accepts the same things. Don't write per-editor parsers. Add each new property an editor writes to `src/css/properties.ts` (default, keywords, negative allowed).
- Viewport widths are explicit: a change is for every width unless the width chip is set. Never infer a range from the window size. Changes record the chip's `widths` through `history.apply(…, { widths })` / `clearProperty(…, widths)`, which the dialog passes for every editor: editors don't handle widths.
- Element states work the same way: the state pills' `states` go through `history.apply(…, { widths, states })` / `clearProperty(…, widths, states)` from the dialog, and fields read values for exactly those states. Editors don't handle states either.
- The history belongs to `mountPilot` (one per page load) and survives reloads: it's saved per tab and found again by selector, or by where it is when its classes changed (`src/edits/persist.ts`, `findTarget()` in `src/dom/target.ts`). Anything new it records must be plain data (JSON-safe) apart from the element, and found again from the change's `target` after a reload.
- A job's prompt comes from the changes the page recorded, never from anywhere else: `formatPrompt()`, fed by `buildChangeSet()` (`src/edits/changeSet.ts`), plus where its elements' code probably is (`whereSection()` and `withComponentFiles()` in `packages/cli/src/locate.ts`, found in the project: the components' files the page couldn't name, and the lines), for speed. There's no Copy prompt: everything goes through a run (Pilot not running is said, not worked around).
- The handoff is jobs ([docs/handoff.md](docs/handoff.md)). The page is the source of truth for its jobs: the hub (`packages/cli`) keeps state in memory only and must accept a job posted again (idempotent by id). Sent changes carry their job id in the history; a job's changes leave the history only through `settle()`, after the page checked them (`edits/verify.ts`): what landed at once, what didn't after its one follow-up (Pilot then accepts the code), and changes it can't check on the agent's word.
- **Never a loader spinning with no clue why.** Anything that waits on something that may never come (an agent, the hub, a check) must say so once it's stuck: what's wrong and what to do, in the places the owner designed (the toolbar's red pills, the elements' corner warning, a red reply in the thread: `PilotSession.stuck`, [docs/handoff.md](docs/handoff.md), *When something's stuck*). A new wait gets its stuck case there too.
- The hub takes jobs only from page origins Pilot runs for (`npx usepilot` registers them), from the `Origin` header; agent routes refuse requests that carry an `Origin`. Keep both checks for every new route.

## Repo conventions

- pnpm workspace (`packages/*`, `apps/*`), TypeScript strict, ESM, `.ts` extensions in relative imports.
- Overlay components: one folder per component, `ui/components/<Name>/` with `<Name>.tsx` + `<Name>.css`. The CSS is wrapped in `@scope (.component-root)` and imported in `ui/styles/index.css` into `layer(components)`. Use px rather than rem. See [docs/development.md](docs/development.md), "Styling".
- **Tokens: use only the `--plt-*` tokens that are actually defined in `ui/styles/tokens.css`.** The project owner maintains that file, and its contents change.
  - Read the file before writing CSS. Don't rely on memory, older versions, or other components, which may still reference tokens that were removed.
  - If no token fits, use a raw value (e.g. `8px`). Don't invent a token, and don't add one to `tokens.css` unless asked.
  - **Ask the project owner before any edit to `tokens.css`**, even one they seem to imply (adding, removing or changing a token's value). Say which token and what would change, and wait for a yes.
  - Tokens hold the shared part only. `--plt-shadow-lg` is drop shadows only: components add their own inset rings in their CSS (`inset 0 0 0 1px …`), since the ring differs per component.
  - `pnpm test` fails on any `var(--plt-…)` that `tokens.css` doesn't define (`ui/styles/tokens.test.ts`).
- **Icons from the project owner** (pasted SVGs) go into `ICONS` in `ui/components/Icon/Icon.tsx`, used through `<Icon name="…" />`, never as raw SVG in a component.
  - One color: draw it in `currentColor`, so it takes the color of the text around it.
  - Several colors: replace each hex with its token from `ui/styles/tokens.css` (e.g. `#E5E5E5` → `var(--plt-color-contrast-high)`, `#1CF69E` → `var(--plt-color-accent)`), keeping any `fill-opacity`. If a color matches no token, ask the project owner instead of keeping the hex.
  - Reuse the shared shapes when they match (the layout frame, the side and gap helpers), and derive the variations that weren't designed (reversed, single side or axis) from the designed one. Say which ones were derived, so the owner can replace them.
- Preact 11 doesn't add `px` to numeric inline styles. Pass strings, using the `px()` helper in `ui/px.ts`.
- Tests are `*.test.ts` next to the source and run with Vitest from the root (`pnpm test`).
- Before finishing a change, run `pnpm typecheck` and `pnpm test`.
- Use `pnpm dev` (playground at :5180) to try overlay changes in a browser.
- To try them in another project, unreleased: `pnpm link-experiment <folder>` once, then `pnpm dev:experiments` (overlay source on :5199, CLI rebuilt on change). [docs/development.md](docs/development.md), "Trying Pilot in your own projects, unreleased".
